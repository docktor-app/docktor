<objective>
Close UAT gap G-10-2 (major): opening a stack's Backups tab fires an endless request storm and makes the page very slow. This plan implements GitHub issue #16 (Phase 10) gap closure. The defect itself is a pre-existing client bug that surfaced during Phase 10's UAT.

Root cause (diagnosed, `.planning/debug/backup-tab-infinite-requests.md`): in `backup-history.tsx`, the polling `useEffect` lists `backups` in its own dependency array while its body writes `backups` via `setBackups(data)`. `getBackups()` -> `apiFetch()` -> `res.json()` returns a brand-new array on every response. So every successful fetch looks like a dependency change, React tears down and re-runs the effect, and the effect's first action is an unconditional fetch. The loop is bounded only by round-trip latency. Secondary symptom of the same defect: the 30 s stop-timer reads `backups` through a stale closure.

The binding fix direction (10-UAT.md G-10-2 `missing`) is: (1) the effect depends on `[stackId]` only; (2) the stop-timer decides from the freshly fetched data (in-closure or a ref), never from the `backups` state. This plan does exactly that. Per CLAUDE.md ("Do not fetch data directly in React components — use a custom hook"; "refactor proactively when touching a module"), the fetch/poll lifecycle moves out of the component into a new `useBackupHistory` hook, where the schedule can be tested with fake timers.

Task 2 adds one refinement, and it is a planner decision (rationale below). The request storm was incidentally keeping the history fresh: a backup started with "Backup Now" (the button directly above the history) appeared right away. With the storm gone, the documented 30 s grace window alone would leave the history stale for a backup started later. The fix uses the stack's live status, which the page already receives over SSE and which always passes through BACKING_UP/RESTORING during a backup/restore. A status change triggers one refresh. That keeps the history fresh with no unbounded polling and no new connection.

Purpose: the Backups tab loads quickly, costs the server a bounded number of requests, and still shows new backups.
Output: a new hook with exact-count tests, a component that only renders, and a one-prop pass-through from BackupsTab.
</objective>

    - Unmount at 5 000 ms: no further `getBackups` calls through 60 000 ms.
