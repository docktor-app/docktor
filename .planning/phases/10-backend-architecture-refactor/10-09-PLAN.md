<objective>
Finish the route-layer pass for the four remaining route files that reach past their layer: `settings.ts` and `notifications.ts` (database client, repositories), `setup.ts` (database client, infrastructure scanner) and `imports.ts` (infrastructure scanner).

These are the same defect class as D-10 and are in scope per PD-4. `setup.ts` carries the highest risk of the four: its first-run flow contains a deliberately non-atomic count-then-create sequence guarded by an exclusive lock row, added under WR-07 to close a real double-submit race. That guard depends on a uniqueness violation propagating to the caller, which is exactly the kind of behaviour a naive "move it into a repository method" refactor destroys.

Purpose: after this plan, every route file in the server calls application services only, and the architecture test enforces it (the rule itself lands in plan 10-10 once the last route file — `backups.ts` — is clean).
Output: four route files with no cross-layer imports, a single encrypted-setting write path, and setup-flow logic behind `OnboardingService`.
</objective>
