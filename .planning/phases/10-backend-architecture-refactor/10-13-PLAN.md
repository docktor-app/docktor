<objective>
Move the `StackEvent` audit-trail writes onto the domain-event bus (D-15 item 2): the file watcher emits a fact, and an audit subscriber turns that fact into a row.

This plan exists because the phase's source audit found D-15 item 2 planned nowhere. `10-PATTERNS.md` specifies the audit-log subscriber's shape in full ("Audit-log subscriber (D-15 item 2, new file)"), `10-RESEARCH.md` names "an audit-log subscriber writes a `StackEvent` row" as one of the three subscribers in its primary use-case trace, and `10-01-PLAN.md`'s phase inventory reserves a row for it — but plans 10-01 through 10-12 migrate notifications (10-12) and status/config broadcasts (10-11) only. Without this plan the phase ships two of D-15's three categories.

Purpose: after this plan, "a stack's configuration changed outside the app" is a fact three independent consumers react to — the live-state bridge, the audit trail, and whatever Phase 14 adds — instead of a sequence of inline calls in a file watcher.
Output: audit fields on the configuration-changed event, an audit subscriber, an ordered subscriber registration, and a file watcher that no longer knows the audit table exists.
</objective>

<plan_decisions>
Decisions taken while planning this plan. They bind this plan and the two that follow it.

- **PD-9 — The audit subscriber writes a row only for the changes that write one today.** The configuration-changed event has two producers after plan 10-11: the file watcher (external edits, which write an audit row today) and `StackService` (in-app edits, which write none). A subscriber that reacted to both would start inserting rows that never existed — new persisted data in a phase whose boundary freezes behaviour. The subscriber therefore keys off the event's own origin discriminator, the same hardcoded literal Phase 08 made required and plan 10-11 kept per call site. The rule is explicit and tested in both directions, not implied by which producer happens to emit.
- **PD-10 — The third audit type named in D-15 item 2 has no producer and gets none here.** The audit enum has three values; grep proves only two are ever written (`git grep -n "createStackEvent" server/src` returns the file watcher's sites only). Creating rows for the third would be new behaviour, not a migration. It is recorded as a finding rather than silently dropped, and rather than invented.
- **PD-11 — The ordering cost is recorded, not absorbed.** Today the audit row is awaited before the live-state frame is published, so a client that refetches the stack's event list on that frame always sees the new row. `emit` does not await handlers (D-16), so after this plan the frame can reach the browser before the insert commits. Registering the audit subscriber ahead of the live-state bridge makes the write *start* first, which is the strongest ordering the bus contract permits; the residual window is named in `<verification>` and checked by a human at the phase gate (plan 10-15). This is the same class of deliberate, recorded consequence plan 10-12 made for the awaited notification sends.
</plan_decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| filesystem -> server | An edit made outside the app crosses into the process and becomes a persisted audit record |
| bus -> audit subscriber -> database | A new indirection between detecting a change and recording that it happened |
| server -> browser | The live-state frame that triggers the client's refetch of the audit log now races the write it describes |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-42 | Repudiation | audit-row write after the indirection | high | mitigate | The audit trail is the only record that a file changed outside the app; a silently non-matching subscription produces silence, not an error. Every one of the three sites keeps a test asserting the emitted event carries the fields its row needs, and the subscriber suite asserts the row content per case against literals copied from the current call sites |
| T-10-43 | Tampering | persisted payload string | high | mitigate | The payload is a serialized string, not a JSON column, so key order is part of the stored value. The subscriber composes keys in the current order and the test asserts the whole string character for character rather than a parsed object |
| T-10-44 | Repudiation | audit rows for changes that write none today | medium | mitigate | PD-9: the subscriber keys off the origin discriminator and is tested in both directions, so an in-app edit cannot start inflating a stack's event log with rows no prior release wrote |
| T-10-45 | Repudiation | write-then-publish ordering | medium | accept | PD-11: `emit` does not await handlers (D-16), so the live-state frame can precede the row's commit. Registration order makes the write start first — the strongest guarantee the bus contract allows — and the residual window is named in `<verification>` and checked by a human at the phase gate rather than absorbed silently |
| T-10-09 | Information Disclosure | bus error logging | medium | mitigate | Unchanged from plan 10-03: the bus logs the event key and the error, never the payload — which here carries file hashes and a parser error message |
