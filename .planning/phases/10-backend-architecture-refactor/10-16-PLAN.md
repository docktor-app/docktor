<objective>
Close two server-side UAT gaps from `10-UAT.md`, both in `server/src/jobs/`, both independent defects with independent fixes. This plan implements GitHub issue #16 (Phase 10 — Backend Architecture Refactor) gap closure.

**G-10-3 (major, UAT test 3):** every 60 s StatePoller reconcile tick re-emits `stack.status_changed` for every known stack even when nothing changed, so the user saw `[NotificationWatcher] Received status change: stackId=docktor-proxy status=RUNNING` repeat forever for a stack that was already RUNNING, and the SSE stream carried a matching redundant `stack_status` "heartbeat" (UAT test 2's note). Root cause (diagnosed, `.planning/debug/status-change-spam-every-tick.md`): `reconcile()` discards `repo.updateStackStatus()`'s return value — which is already `null` when the status is unchanged — and emits unconditionally. `handleEvent()` one method above already uses the correct pattern. Pre-existing, not a Phase 10 regression; fixed now because UAT surfaced it on the D-15 bus path.

**G-10-1 (major, UAT test 1):** the startup log never names ProxyCertPoller (nor StatePoller, DiskChecker, UpdateChecker). Root cause (diagnosed, `.planning/debug/missing-proxycertpoller-log.md`): nothing in the Job abstraction (D-02/D-13) or the registry (D-14) logs a start line by design; the three jobs that do print something at start do so by accident of their own job-specific logging. UpdateChecker genuinely lost its start line in plan 10-07. The fix is one deliberate line per job at true start time, emitted by `JobRegistry.startAll()` — the single place every job kind (interval, watcher, and the `dynamic` BackupScheduler that implements `Job` directly) passes through, so all seven are covered by construction.

Purpose: operators can confirm at a glance that every background job came up, and the notification log and live-state stream only speak when a stack's status actually changed.
Output: a guarded emit in `state-poller.ts`, a started line in `job-registry.ts`, and unit tests that pin both behaviors (including the exact user-visible symptom, reproduced end-to-end through the real bus and the real NotificationWatcher).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Docker daemon -> StatePoller | Container list and labels are read from the local Docker API (unchanged by this plan). |
| server process -> stdout/log sink | New start-time log lines are written to the process's console, which operators and any log shipper read. |
| domain-event bus -> SSE stream | `stack.status_changed` reaches browsers via state-broadcast-subscriber.ts (unchanged; this plan only reduces how often it fires). |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-16-01 | Information disclosure | `JobRegistry.startAll()` started line | low | accept | The line prints only `job.name` and `job.kind`, which are compile-time string literals (`"StatePoller"`, `"interval"`, ...). No config, env var, path, credential, or error object is interpolated. This matches T-10-11's existing rule that the registry never stores or prints job config. |
| T-10-16-02 | Denial of service | `StatePoller.reconcile()` emit volume | low | mitigate | Gating the emit on `updateStackStatus()`'s non-null return removes one redundant bus dispatch, one NotificationWatcher log line, and one SSE write per stack per 60 s tick. Pinned by the Task 1 test asserting zero emits on an unchanged tick. |
| T-10-16-03 | Tampering | `stack.status_changed` payload shape | low | mitigate | The payload stays exactly `{stackId, status}` for real transitions. The Task 1 test asserts it with `toEqual` (no extra keys), so SSE consumers see byte-identical events for real transitions. |
| T-10-SC | Tampering | npm/pip/cargo installs | high | mitigate | Zero packages installed. This plan only edits two existing source files and three existing test files, and adds no imports from outside the repo. |

## Accepted behavioral trade-off (not an attacker threat)

After G-10-3, the reconcile tick no longer re-broadcasts an unchanged status every 60 s. A browser whose EventSource dropped during a real transition used to be silently re-synced by that redundant event. Now it re-syncs on the next real transition or on page load. Accepted: the redundant event was the reported bug, `useContainerEvents` relies on native EventSource auto-reconnect, and every real transition still emits.
</threat_model>
