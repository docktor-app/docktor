**Implements:** [docktor-app/docktor#23](https://github.com/docktor-app/docktor/issues/23) — the "a service can optionally be configured with an HTTP health-probe URL" half of success criterion 1 (D-01, D-02, amended D-05 host guard). The probe engine that reads this config ships in 14-06. Note for the issue: #23 mentions an "expected status code" field; D-02 deliberately replaces it with "any 2xx/3xx is healthy", so the issue text should be updated when this phase closes.

No SPEC.md exists for this phase, so no probe-derived predicates were generated. The UI-SPEC `## UI Considerations` rows for the probe form are lifted into must_haves.

<objective>
Let a user switch on an HTTP health probe for any service from the stack's Config tab, entering a URL and optional timeout. The change lands in the compose file (YAML stays the single source of truth) and goes through the same diff-confirm review as any compose edit.

Purpose: D-01 locks the config location (`x-docktor: health-probe:` inside each service), and the amended D-05 restricts the probe host to the service's own container (SSRF guard). This plan owns the shared schema that enforces both, so 14-06's server-side parser and transport reuse it verbatim. It also owns the form that writes the block without corrupting the rest of the file.

Output: shared probe schemas, a client YAML helper, one form section component, and the ConfigTab mount, with unit, regression and e2e tests.
</objective>
