**Implements:** [docktor-app/docktor#23](https://github.com/docktor-app/docktor/issues/23) — the retained per-service health history (D-12 amended) and the health-state stability fix (RESEARCH Finding 4) that #23's notification criterion and #24's uptime depend on.

<objective>
Make per-service health transitions a durable, queryable history. This plan uses the source that already exists, Docker healthchecks. 14-06 adds HTTP probes as a second source over the same pipeline.

The pipeline: StatePoller sees a service's Docker health change, writes the Service row, then emits a new `service.health_changed` domain event. A dedicated subscriber appends a `ServiceHealthEvent` row keyed by `(stackId, serviceName)`, so the row survives the delete-and-recreate of Service rows on every deploy. `GET /api/stacks/:id/health-events` serves the history to the client (14-03 renders it).

Task 2 fixes the existing defect that makes the history and the stack status unreliable. `StatePoller.reconcile()` overwrites every service's health with null every 60s, which flaps HEALTHY/UNHEALTHY stacks to RUNNING and cancels NotificationWatcher's UNHEALTHY timer. The task also records transitions observed by reconcile and the post-deploy catch-up.

Output: one Prisma model + enum + migration, a pure domain helper, one domain event, one subscriber, one repository, one read service, one route file, and the shared query schema.
</objective>
