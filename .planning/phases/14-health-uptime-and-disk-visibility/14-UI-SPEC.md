# Phase 14 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

Scope: five client surfaces plus one settings card, all built on Phase 11 primitives. (1) New **Storage** page, (2) per-stack **Uptime / Incidents / Disk** row and **Incident list** on the stack Overview tab, (3) per-service **health history** inside the Services section, (4) **HTTP Health Probes** form on the Config tab, (5) **Uptime column** on the stack list (Dashboard + Stacks page), (6) **Health History retention** card in Settings > Stacks.

Accent reserved for: (1) the `Save Health Settings` primary button, (2) the active `Storage` item in the sidebar (existing `isActive` styling), (3) the keyboard focus ring (`--ring`). Nothing else uses accent; sort headers, chevrons and links stay `foreground` / `muted-foreground`.

Semantic status tones are separate from the accent and always go through `ToneBadge` / `StatusDot`, with `dark:` counterparts already built in. Any direct color utility added for a number (StatCard `valueClassName`) must be the pair `text-{color}-600 dark:text-{color}-400`, exactly as `dashboard-stat-cards.tsx` does.

| Signal | Tone mapping |
|--------|--------------|
| Uptime percentage (badge and StatCard value) | 99.9% or more: green. 99% up to below 99.9%: yellow. Below 99%: red. No data (null): neutral, em dash |
| Service health event status (`toStatus`) | `healthy` green, `unhealthy` red, `starting` yellow, `null` (cleared) neutral |
| Incident cause | `UNHEALTHY` / `ERROR` via `StackStatusBadge display="compact"` (red) |
| Ongoing incident marker | `ToneBadge tone="red"`, no pulse |
| Health source (`HTTP probe`, `Docker healthcheck`) | `ToneBadge tone="neutral"` |
| Storage sizes, totals, share | No tone; plain foreground text |

Color is never the only signal: every dot or tone is paired with a text label or a number.

## Surface and Interaction Contracts

### A. Navigation and routes
- Route `/storage` registered in `router.tsx` under the protected layout. Sidebar item `Storage` (lucide `HardDrive`) sits between `Stacks` and `Settings`. Active state uses the existing `startsWith` logic.
- Breadcrumb: `Storage` as `BreadcrumbPage`, same shape as the Stacks page.

### B. Storage page (D-15, D-14 amended)
Order inside `PageContent`: stale-measurement warning Alert (only when `measuredAt` is older than 48 hours), totals row, Stacks Section, Backups Section.
1. **Totals** — `grid grid-cols-1 gap-4 sm:grid-cols-3` of three StatCards: Total Disk Used (`HardDrive`), Stack Volumes (`Database`), Local Backups (`Archive`). Grand total is volumes plus backups (never the whole stack directory), so nothing is counted twice. The `Last measured` stamp sits in `PageDescription`-adjacent muted 12px text under the page title.
2. **Stacks Section** — `Table` with columns `Stack` and `Size`, plus a leading narrow expander cell.
   - Default sort Size descending. Column headers are `Button variant="ghost" size="sm"` containing the label and an `ArrowUp` / `ArrowDown` / `ArrowUpDown` icon (aria-hidden); the `<th>` carries `aria-sort` (`ascending`, `descending`, or `none`). First click on a new column applies its natural direction (Name ascending, Size descending); clicking again reverses. Ties break by name ascending. Unmeasured stacks always sort last, in both directions. Sorting is client-side, no pagination.
   - Stack name is a `Link` to `/stacks/{id}` (the row itself is not clickable).
   - Expander: icon `Button` (ChevronRight rotated 90 degrees when open, `transition-transform motion-reduce:transition-none`) with `aria-expanded`, `aria-controls` pointing at the child-row group, and label `Show volumes for {stack}` / `Hide volumes for {stack}`. Hidden (replaced by an equal-width spacer) when the stack has no volumes. Default collapsed; several rows may be open at once.
   - Child rows: one per volume, `bg-muted/50`, name indented `pl-8`, size right-aligned. They use the same sort key and direction as the parent table. A volume name that is too long truncates with a `title` attribute.
3. **Backups Section** — `Table` with `Stack` and `Size` columns, one row per stack that has a local backup repository, sorted by size descending, with a `TableFooter` row `Backups subtotal`. No sort controls (secondary list). Remote-only repositories never appear.
- Formatting: `formatBytes(bytes: number)` in `lib/format-bytes.ts` uses base-1024 with the app's existing labels (`B`, `KB`, `MB`, `GB`, plus `TB`), one decimal for KB and MB, two for GB and TB, `0 B` for zero, and en dash for null. The existing `formatSize` (string input, backups-specific) stays; the planner may make it delegate.
- Measured-total rule: stacks with a null measurement are excluded from totals; if nothing is measured, totals read `—`.

### C. Stack Overview additions (D-16, D-15 stack figure)
- `OverviewTab` order: `UptimeCard` row, `ServicesSection`, `IncidentList`, `ActivityTimeline`, with the existing `space-y-8`.
- `UptimeCard` renders `grid grid-cols-1 gap-4 sm:grid-cols-3` of three StatCards: Uptime (`Activity`, value tone from the table above via `valueClassName`), Incidents (`AlertTriangle`, count, `text-red-600 dark:text-red-400` only when count is greater than 0), Disk Used (`HardDrive`, `formatBytes(volumeSizeBytes)` read from the stack detail already loaded, `—` when null).
- Uptime value format (`lib/uptime-format.ts`): null gives `—`; exactly 100 gives `100%`; otherwise truncate (never round up) to one decimal, so 99.96 reads `99.9%` and a stack with any measured downtime never displays `100%`.
- `IncidentList` is a flat Section with a `Table` inside a `max-h-96 overflow-y-auto` wrapper, newest first. Ongoing duration is computed from now and recomputed on a 60-second tick; closed duration is `resolvedAt - createdAt`. `lib/format-incident-duration.ts`: under 60s `{s}s`, under 1h `{m}m {s}s`, under 24h `{h}h {m}m`, otherwise `{d}d {h}h`.
- Refetch uptime and incidents whenever `stack.status` changes (the existing SSE-driven stack refresh already updates it); no new SSE type and no polling.

### D. Service health history (D-12 amended)
- `ServicesSection` gains a third icon button in the actions cell, lucide `History`, same size and Tooltip pattern as the existing buttons, with `aria-expanded`. Opening it inserts a `TableRow` directly below with one `TableCell colSpan={6}` (`bg-muted/50`) containing `ServiceHealthTimeline`.
- Data: one `useServiceHealthEvents(stackId)` call in `OverviewTab` fetches the stack's latest events once (all services) and passes each service its slice; no per-service request. The panel shows that service's latest 50 events, newest first, in a `ScrollArea` capped at `h-48`.
- Row layout mirrors `activity-timeline.tsx` `TimelineRow`: stacked on phone, one line from `sm`. Marker = `StatusDot` with the tone of `toStatus` (static, never pulsing). Then timestamp (12px muted), `{from} → {to}` text (body), source `ToneBadge`, message (muted, `break-words`).
- The status cell shows a neutral `HTTP probe` `ToneBadge` next to `ServiceStatusBadge` only when that service has at least one HTTP probe event (RESEARCH Open Question 4; no DB probe column).
- `getServiceStatusPresentation` adds `running` + `starting`: label `starting`, tone yellow, `dotPulse` false, so the 60-second grace period is visible and matches the timeline vocabulary. This changes an existing presentation; its unit tests and any Playwright fixture using `starting` must be updated in the same plan.

### E. Config tab probe form (D-01, D-02, D-07, D-08, amended D-05 hosts)
- New flat Section `HTTP Health Probes`, placed between Compose File and Environment Variables, with a `Separator` on each side as the Config tab already does. It has no Save button of its own.
- One `divide-y` list row per service parsed from the compose buffer: service color dot (`getServiceColor`), service name, and the `Probe {service} over HTTP` Switch. When on, the row reveals a `sm:grid-cols-[1fr_160px] gap-4` pair: `Probe URL` and `Timeout (seconds)`.
- Built with react-hook-form and the shared Zod schema through `standardSchemaResolver`. Field changes that validate are written immediately into the compose buffer via `files.setComposeContent` using the `yaml` Document API (`setIn` / guarded `deleteIn`, comments preserved, as `compose-proxy-editor.ts` does); invalid values show inline `FormMessage` text and do not write. Turning the switch off removes the `health-probe` key and prunes an empty `x-docktor` map. Errors appear after blur or submit, not on first keystroke.
- Two-way sync rule: the form must tell its own buffer writes apart from external edits made in the code editor, and re-seed only on external ones. This is the same failure class as the 11-12 EnvEditor line-duplication regression and needs a dedicated regression test.
- The probe dirties the compose buffer, so the existing Save routes through `DiffConfirmDialog` and `UnsavedChangesGuard` with no changes. The form is disabled behind the YAML-error Alert while the buffer does not parse.
- The always-visible behavior note states cadence, threshold, grace period, 2xx/3xx rule and override semantics (D-06, D-07, D-08, D-02) so users know exactly what the probe does.
- The timeout field is included as RESEARCH Assumption A7 describes; if the planner drops it, remove the field, its label, its description and its error copy together.

### F. Stack list Uptime column (D-16)
- `StackList` gains an `Uptime` column between `Status` and `Services`, rendered by `UptimeBadge` (a `ToneBadge` with the formatted percent and `title` `Uptime over the last {N} days`). The column renders only when an `uptimes` prop is supplied; `Dashboard` and `StacksPage` both supply it from one `useStackUptimes()` hook (`GET /api/uptime/stacks`). `StackList` stays data-free (props in, JSX out), per CLAUDE.md.
- Loading: `Skeleton h-5 w-12` in the cell. Failure of the batch endpoint degrades silently to `—` (non-critical, no toast). Phone width: the existing DataTable card layout shows it as an `Uptime` label/value row.

### G. Settings retention card (D-10)
- `HealthRetentionCard` is a Card (settings group, per CLAUDE.md) at the end of Settings > Stacks, after `TemplateReposCard`. Structure copied from `ComposeChecksCard`: react-hook-form, `standardSchemaResolver` with the shared `healthSettingsSchema` (integer 1 to 365), `Skeleton` while loading, `toast.promise` on save, `CardFooter` Save button. The retention-shortening AlertDialog gates the submit when the value decreases.

### H. Accessibility, motion, and test hooks
- Every icon-only button has an `aria-label`; `StatusDot` is `aria-hidden`, so each dot sits beside a text label. No new animation is introduced; existing `motion-reduce` handling on `ToneBadge` and `StatusDot` is relied upon. Tab order follows DOM order; sort headers and expanders are native buttons reachable by keyboard.
- Dark mode is a tested surface: every light-only color utility added must have its `dark:` pair; verify the Storage page, Overview row and probe form in both themes.
- Phone width (Pixel 7 project): Storage tables have two columns and fit without scrolling; the incident table scrolls horizontally inside its container with `whitespace-nowrap` on `Started` and `Ended`; StatCard rows collapse to one column.
- Every new endpoint needs a default stub in `client/test/integration/fixtures.ts` or the unstubbed-request guard fails every spec that visits the Dashboard, a stack Overview, or Settings.
