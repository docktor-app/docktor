> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope note — read before anything else

Phase 7 has exactly one item with a UI dimension: **item 2, "Brownfield import/adopt is
unreachable after setup wizard closes."** Items 1 (backup wedge-state) and 3 (mount-point
verification) are pure backend fixes with no UI surface and are intentionally absent from this
document.

greenfield design brief — it documents the **as-built contract** as the locked design, verified
against the running implementation, so `gsd-ui-checker` can validate it and `gsd-planner` can
scope Phase 7's actual remaining work correctly (see Recommendation below).

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background` (oklch(1 0 0) light / oklch(0.145 0 0) dark) | Page body |
| Secondary (30%) | `--card` / `--muted` | Card surface wrapping the scan form and results table, skeleton fills |
| Accent (10%) | `--primary` (near-black light / near-white dark, neutral base color — this is a **grayscale** shadcn theme, not a hue accent) | "Scan" button, "Adopt" button, primary Dialog "Confirm & Migrate" action |
| Destructive | `--destructive` (oklch(0.577 0.245 27.325)) | Reserved — not currently used in this flow (no destructive action exists here; adopt/migrate are additive, not deletive) |

Accent reserved for: the single primary call-to-action per view — "Scan" (initial state),
"Adopt" (per-row primary action), "Confirm & Migrate" (dialog step 2). "Migrate" and "Import
Existing Stack" itself are secondary (`variant="outline"`) since "Create Stack" remains the
page's dominant action.

Ad-hoc color note (pre-existing, not introduced by this phase): `CompatibilityBadge` and the
config-error/config-changed pills in `stack-list.tsx` use raw Tailwind color utilities
(`bg-green-100 text-green-800 dark:bg-green-900 …`, `text-yellow-600 dark:text-yellow-400`)
rather than the `--chart-*`/semantic tokens. This is an existing project-wide pattern, not a
Phase 7 defect — do not "fix" it as part of any Phase 7 plan; flag it instead for the Phase 10
UX-redesign backlog if it needs remediation.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (entry point) | "Import Existing Stack" (button, `FolderInput` icon, outline variant, `stacks/index.tsx`) |
| Primary CTA (scan) | "Scan" (button, `Search` icon) |
| Primary CTA (per-row adopt) | "Adopt" / "Adopting…" while in flight |
| Primary CTA (per-row migrate) | "Migrate" (opens `MigrationWizard` dialog) |
| Empty state heading | "No stacks found" |
| Empty state body | "We couldn't find any docker-compose.yml files in the directories you specified. Check the paths and try again." |
| Loading state | Three `Skeleton` rows (10px height, full width) while `scanning === true`; button label switches to "Scanning…" |
| Error state (scan failure) | `toast.error(message)` — server error message passed through verbatim, e.g. permission or filesystem errors from `BrownfieldScanner` |
| Error state (adopt conflict) | `toast.error(message)` — surfaces `ConflictError`'s message verbatim: `Stack "<slug>" already exists` |
| Error state (adopt — other failure) | `toast.error(message)` falling back to `"Failed to adopt stack"` if the thrown value isn't an `Error` |
| Error state (migration preview failure) | `toast.error(message)` falling back to `"Failed to generate preview"` |
| Error state (migration execute failure) | `toast.error(result.error \|\| "Migration failed")` |
| Success state (adopt) | `toast.success("<name> adopted successfully")` with a "View stack" action button navigating to `/stacks/:id` |
| Success state (migrate) | `toast.success("Migration complete! <name> is now managed by Docktor")` with the same "View stack" action |
| Already-adopted row state | Row's action cell replaced with static text "Imported" (green, no interactive control) — this is the UI's answer to "already-adopted conflict" for a row adopted **in the current session**; a conflict against a *prior* session's adoption instead surfaces via the toast error above, since the scan result has no way to know in advance |
| Destructive confirmation | None in this flow — adopt/migrate are additive operations with no delete/overwrite path, so no destructive-confirmation dialog exists or is needed |

## UI Considerations

Applicable state considerations resolved: 7 covered, 0 backstop, 1 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Scan results table | ✅ covered | Documented "No stacks found" empty state renders when `scanned && !scanning && stacks.length === 0` |
| loading | Scan results table | ✅ covered | Three `Skeleton` rows render while `scanning === true`; button switches to "Scanning…" and disables |
| error | Scan action | ✅ covered | Any thrown error from `scanDirectories` surfaces as `toast.error(message)` — verbatim server message |
| error | Adopt action (conflict) | ✅ covered | `ConflictError` from a duplicate slug surfaces its exact message via toast; the row stays actionable (no state left half-applied) |
| error | Migration execute (partial failure) | ✅ covered | `executeMigration` returning `{success:false, error}` surfaces via toast and never marks the row "Imported" — `MigrationService` (server-side, item 3's neighbor, not this phase's scope) owns rollback-on-failure per BF-05 |
| populated | Scan results table | ✅ covered | Standard `Table` rendering with per-row `CompatibilityBadge`, service count, and Adopt/Migrate actions |
| zero-one-many | Scan results table | ✅ covered | Zero → empty state; one-or-many → identical table row rendering, no singular/plural copy bug (`"director{y/ies}"` correctly pluralized in the skipped-directories note) |
| long-text | Directory paths / compose paths | ⚠ unresolved | `TableCell` renders `stack.directory` in `font-mono text-sm` with no `truncate`/`max-w` guard — a very long host path (e.g. deeply nested NFS mount) could overflow the table cell on narrow viewports. Pre-existing in the shipped implementation; not introduced by this phase. Planner should treat as an assumption (acceptable — self-hosting operators' directory trees are typically shallow) unless UAT surfaces a real overflow case. |
