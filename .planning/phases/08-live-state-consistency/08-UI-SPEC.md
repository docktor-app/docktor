## Scope Reality Check (read this first)

Codebase inspection (not just the todo files) shows that **all three of Phase 8's scoped
todo items are already code-complete** on this branch, shipped by Phase 05.1:

| Todo | Backend | Client wiring | Visual indicator | What's actually left |
|------|---------|---------------|-------------------|----------------------|
| `config-error-ui-indication-missing` | `Stack.configError` persisted, set/cleared (05.1-06) | `use-stack.ts`/`use-stacks.ts` handle `config_error` SSE (05.1-06) | Destructive `Alert` on detail page + red pill in `stack-list.tsx` (05.1-06) | Live human verification only (05.1-06 D9, never executed — no running instance in that session) |
| `env-file-changes-dont-flag-config-changed` | `updateStack()` env branch flags `configChanged` + `FileWatcher` watches `.env` via `lastEnvHash` (05.1-02, 05.1-06) | `config_changed` SSE handled identically to compose changes | Yellow `Alert` / pill (shared with compose path) | Live human verification only (05.1-02 D6, 05.1-06 D9) |
| `manual-actions-dont-broadcast-sse` | Every `StackService`/`BackupService` transition publishes `stack_status` via `transitionStatus()` wrapper (05.1-02, 05.1-04) | `useStack`/`useStacks` already consume `stack_status` | `StackStatusBadge` re-renders on the pushed status | Live human verification only (05.1-02 D6) — **plus one real visual gap identified below** |

This UI-SPEC therefore does **not** design new screens or new components. Its job is to:
1. **Lock the existing visual language** (badges/alerts/toasts already shipped) as the contract, so
   the executor does not redesign or duplicate it while closing out the remaining verification work.
2. **Specify the one concrete visual inconsistency** this phase's own live-verification work will
   expose: `BACKING_UP`/`RESTORING`/`MIGRATING` states have no "in progress" motion cue, unlike
   `DEPLOYING`/`UPDATING` — see Color section.
3. **Flag one adjacent state-guard gap** (Deploy button not disabled during `UPDATING`/`MIGRATING`)
   as an unresolved UI consideration for the planner — it is not one of the 3 scoped todos, so this
   spec does not mandate a fix, only surfaces it so it isn't silently missed if the planner decides
   it's in-scope for closing this phase's UAT.

If a fix is required during 05.1-02/05.1-06's still-open `human_judgment: true` verification items
(cross-tab live check, external `.env` edit, YAML syntax error injection), the executor uses the
existing components below — never new ones.

## Color

Base theme is shadcn's neutral palette (`client/src/index.css`, oklch tokens) — this phase does not
introduce new theme tokens. The dominant/secondary/accent split below documents the existing app
theme for reference; the semantic status-color table beneath it is what Phase 8 actually governs.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background` / `--card` (near-white, `oklch(1 0 0)`) | Page background, card surfaces |
| Secondary (30%) | `--secondary` (`oklch(0.97 0 0)`) | Muted card headers, sidebar, nav |
| Accent (10%) | `--primary` (near-black, `oklch(0.205 0 0)`) | Primary action buttons only (e.g. the Deploy button) — never status indicators |
| Destructive | `--destructive` (`oklch(0.577 0.245 27.325)`, red) | Destructive actions (Delete) and the `config_error` indicator only |

Accent reserved for: the primary `Deploy`/`Redeploy` button in `StackActions`, and focus rings.
Status badges/pills use the separate semantic status-color language below, layered on top of the
neutral theme — they are deliberately **not** styled with `--primary`/`--accent`.

**Status color language (locked, additive to the theme above — this is the actual contract for
Phase 8):**

| State bucket | Statuses | Treatment | Source |
|---|---|---|---|
| Healthy / running | `RUNNING`, `HEALTHY` | Green (`bg-green-500/15 text-green-700 border-green-500/25`) | `stack-status-badge.tsx` (existing, unchanged) |
| Error | `ERROR`, `UNHEALTHY` | Red (`bg-red-500/15 text-red-700 border-red-500/25`) | existing, unchanged |
| Stopped / draft | `STOPPED`, `DRAFT` | Gray (`bg-gray-500/15 text-gray-700 border-gray-500/25`) | existing, unchanged |
| **In progress (action)** | `DEPLOYING`, `UPDATING` | Blue + `animate-pulse` (`bg-blue-500/15 text-blue-700 border-blue-500/25 animate-pulse`) | existing, unchanged |
| **In progress (maintenance) — GAP** | `BACKING_UP`, `RESTORING`, `MIGRATING` | Currently plain `outline` variant, **no color, no motion** — inconsistent with the identical "something is happening right now" semantics of `DEPLOYING`/`UPDATING` | **Fix required by this phase**: add `animate-pulse` (motion only, keep the existing gray/`outline` look — do not switch these to blue, which is reserved for user-initiated deploy/update actions vs. these maintenance operations) to `statusColors` in `stack-status-badge.tsx`: `BACKING_UP: "animate-pulse"`, `RESTORING: "animate-pulse"`, `MIGRATING: "animate-pulse"` |
| Config changed (independent flag, not a `StackStatus`) | `stack.configChanged` | Yellow (`bg-yellow-100 text-yellow-800 dark:bg-yellow-900 dark:text-yellow-200` — pill in `stack-list.tsx`; `Alert` with matching yellow override in `[id].tsx`) | existing, unchanged |
| Config error (independent flag, not a `StackStatus`) | `stack.configError` | Red (`bg-red-100 text-red-800 dark:bg-red-900 dark:text-red-200` pill; destructive `Alert` variant on detail page) | existing, unchanged |

Rationale for the fix: this phase's entire purpose is making already-correct server state show up
live. Once `BackupService`'s `stack_status` broadcasts are confirmed live end-to-end (05.1-04,
pending this phase's human verification), a user watching the stack list during a live backup/
restore/migration will see the badge change to `BACKING_UP`/`RESTORING`/`MIGRATING` in real time —
and with no motion cue, a static badge reads as "stuck," not "working." Do not invent a new color for
this — reuse the existing pulse mechanism exactly as `DEPLOYING`/`UPDATING` already do, changing only
the presence of `animate-pulse`, never the badge's variant or base color.

## Copywriting Contract

All copy below is already shipped and must not be reworded by this phase's executor — it exists
purely so the contract has a single place recording what's locked:

| Element | Copy |
|---------|------|
| Config-error alert (detail page) | `Configuration file has an error: {stack.configError}` (destructive `Alert`) |
| Config-error pill (list view) | `config error` (fixed label, red) |
| Config-error toast (SSE push, other tabs) | `{event.message}` verbatim (the parser's own error text), red toast |
| Config-changed alert (detail page) | `Configuration has changed since last deployment. Re-deploy to apply changes.` (yellow `Alert`) |
| Config-changed pill (list view) | `config changed` (fixed label, yellow) |
| Config-changed toast (SSE push, other tabs) | `Configuration file changed externally` (yellow toast) |
| Deploy action toast | loading: `Deploying...` / success: `Deploy completed` / error: `{err.message ?? "Deploy failed"}` |
| Stop action toast | loading: `Stopping...` / success: `Stack stopped` / error: `{err.message ?? "Stop failed"}` |
| Restart action toast | loading: `Restarting...` / success: `Stack restarted` / error: `{err.message ?? "Restart failed"}` |
| Update Images toast | loading: `Updating images...` / success: `Images are already up to date` or `Images updated successfully` / error: `{err.message ?? "Update images failed"}` |
| Backup Now toast | success: `Backup started` (with a "View progress" action) / error: `{err.message ?? "Backup failed"}` |
| Backup-in-progress menu item | `Backup in progress...` (replaces `Backup Now` label when `status === "BACKING_UP"`) |
| Destructive confirmation | Delete stack: native `confirm()` dialog, `Delete stack "{stackName}"?` — **pre-existing pattern, not shadcn `AlertDialog`**; out of this phase's scope to change (tracked separately under the Phase 10 component-reuse audit, not Phase 8) |

No new copy is needed for this phase's actual scope (SSE-liveness + verification). If the
`BACKING_UP`/`RESTORING`/`MIGRATING` pulse fix above is implemented, it requires zero new copy — it
is a CSS-class-only change.

## UI Considerations

Applicable state considerations resolved: 4 covered, 0 backstop, 2 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| long-text | Config-error `Alert` description (`[id].tsx`) | ✅ covered | `AlertDescription` has no `line-clamp`; a multi-line YAML parser error wraps in place, never truncates — confirmed in `alert.tsx` |
| zero-one-many | `configError` + `configChanged` shown together | ✅ covered | Both flags are independent (verified against `stack-status-machine.ts` in 05.1-06); both `Alert`s render stacked when both are true — no mutual exclusion |
| partial | Live SSE push arriving while the user has unsaved edits in the Compose/Env textarea | ✅ covered | `composeDirty`/`envDirty` guards in `[id].tsx`'s effect prevent a background refetch from clobbering in-progress local edits |
| overflow | Multiple browser tabs open on the same stack during a manual action | ✅ covered | `stack_status`/`config_changed` SSE events are broadcast to every subscriber, not just the acting tab (05.1-02 D1, D6) |
| overflow | Deploy button (`StackActions`) not disabled during `UPDATING`/`MIGRATING` — `BLOCKED_STATES` only lists `BACKING_UP`/`RESTORING`/`DEPLOYING` | ⚠ unresolved | Not one of Phase 8's 3 scoped todos; server-side `assertTransition()` still rejects the conflicting action, so this is a UX rough edge (confusing error toast), not a data-safety issue. Planner should treat as an assumption: fix only if the phase's own live-verification pass surfaces it as user-visible confusion, otherwise defer. |
| long-text | Config-error red pill (list view) shows a fixed `config error` label, never the message itself | ⚠ unresolved | Deliberate existing design (avoids truncation/overflow in the table row) — full message is only on the detail page's `Alert`. Acceptable as-is; flagged only so a future hover-tooltip enhancement isn't treated as a Phase 8 requirement. |
