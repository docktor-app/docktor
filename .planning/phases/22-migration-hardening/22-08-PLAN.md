Implements the restart-recovery part of GitHub issue docktor-app/docktor #100 (D-06) and the "after a Docktor restart" case of #105. With this plan the phase PR closes `Closes #100`, `Closes #101`, `Closes #102`, `Closes #103`, `Closes #104`, `Closes #105`, `Closes #107`, `Closes #108`, `Closes #109`.

<objective>
Persist the rollback ledger as a migration journal and recover interrupted migrations on boot by running the same rollback, so a Docktor restart mid-migration puts the original stack back and the user sees how it ended.

Purpose: ROADMAP SC#3 ("or Docktor restarts in the middle of a migration") and SC#5 (toast terminal after reload/reconnect), MIG-08, MIG-11, D-06. The file journal lives in the stacks directory, which the boot sequence already verifies is mounted and persistent, so recovery does not depend on the database being reachable.
Output: journal schema, MigrationJournalPort + MigrationJournal, JournaledMigrationLedger, MigrationOperationService.recoverInterrupted, MigrationRecoveryService, boot wiring in index.ts, changelog entries.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Persistent stacks directory -> boot recovery | journal files are read at boot and drive renames, directory removal and record deletion |
| Process crash -> user's production stack | a crash can leave the old stack stopped and the original renamed aside |
