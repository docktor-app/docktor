## Discretion Decisions (this phase)

CONTEXT.md's "Claude's Discretion" section left the exact moving-tag copy/tone, the disabled-
Upgrade UX details, and the Update Images wiring mechanism (callback prop vs. direct API call) to
this contract and the planner. Resolved here:

1. **Moving-tag copy split across two locations, not one block:** the *why* ("no fixed version to
   select") lives in the `DialogDescription` (replacing the generic description for this state
   only, since the generic description is actively misleading here — it promises "choose a
   version"); the *what to do instead* ("Update Images pulls the newest image... stack-wide") lives
   in the new `Alert` body, right next to the button that does it. Splitting this way means a user
   skimming just the dialog header still gets the correct mental model before reading further.
2. **Alert `variant="default"`, not a colored info treatment:** `components/ui/alert.tsx` only
   defines `default`/`destructive` — there is no blue/informational variant to reach for, and
   inventing one (e.g. copying `stack-alerts.tsx`'s yellow `configChanged` override) would
   introduce a third ad-hoc color just for this one message. Plain `default` (neutral card
   surface) is correct and makes the point: this is context, not a warning.
3. **"Update Images" button is `variant="outline"`, not the primary accent color:** the dialog's
   one true primary action is `Upgrade`. Even though `Upgrade` is disabled in this state, giving
   "Update Images" the accent treatment would make it look like the dialog's main action, when
   it's actually a shortcut out of a dead-end state. Outline keeps the visual hierarchy honest.
4. **Update Images wiring: direct API call, not a threaded callback.** `service-upgrade-dialog.tsx`
   already imports `getServiceTags`/`upgradeService` directly from `@/lib/stacks-api` — this file
   already establishes the "page-scoped component calls the API client directly" pattern (mirrors
   `stack-actions.tsx`'s own `updateImages` import). Importing `updateImages` as a third function
   from the same module is the smallest diff and matches this file's own precedent; no new prop
   needs to thread through `OverviewTab` → `ServicesSection` → `ServiceUpgradeDialog`.
5. **Dialog closes synchronously on click, toast reports the outcome after:** mirrors
   `stack-actions.tsx`'s `handleUpdateImages` (a dropdown menu item that dismisses on click while
   the `toast.promise`-wrapped mutation runs in the background) rather than this file's own
   `handleConfirm` pattern (which keeps the dialog open until the mutation resolves). The
   moving-tag button's label and action are read-only/safe to fire-and-forget — keeping the dialog
   open while a stack-wide pull+redeploy runs would block the user from doing anything else on the
   page for no benefit.
