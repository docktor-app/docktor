<objective>
Make the `.env` extraction preserve every service's effective environment.

Purpose: the rewrite moves inline `environment` literals into `.env` and replaces them by `${KEY}`. Today all literals share one `Map<key, value>`, so `PORT: "80"` in one service and `PORT: "9000"` in another both read the last value, and a key already in the old `.env` can be overridden by the appended block. Found while planning, in the same failure class (the effective value silently changes): `DockerExecutor` runs `docker compose` with Docktor's own process environment (execFile without an `env` option) and compose gives shell variables precedence over `.env`, so an extracted `${PORT}`, `${TZ}` or `${DATABASE_URL}` would resolve to Docktor's own value (for DATABASE_URL: Docktor's database credentials inside the migrated container); compose also reads `COMPOSE_*` from `.env` to configure itself; and a new `.env` name changes every other `${NAME}` reference in the compose file. WR-09: keys such as `spring.datasource.url` become invalid `${...}` references, and values with newlines, quotes or `$` change meaning once dotenv parses them.
Output: a pure dotenv format module, a name allocator in the rewriter that never reuses a name with a different meaning, the old `.env` passed into the rewrite from preview and execute, tests.

Out of scope: WR-02 (setup-route authentication, deferred human decision), WR-06 (masking the compose diff), and Docktor's general behaviour of running compose with its own environment for stacks that already contain `${VAR}` references (reported as a follow-up, not part of this gap).
</objective>
