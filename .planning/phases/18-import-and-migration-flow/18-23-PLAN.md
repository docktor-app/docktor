**GitHub issues:** [#72 Migration dialog: real diff, explicit backup, stop old stack](https://github.com/docktor-app/docktor/issues/72) (found while re-testing the old-stack stop; the defect is in the shared live-state path, so every stop benefits). Gap closure round 3 for **18-UAT.md G-18-23-stop-ui** ("Stopping a stack's containers is reflected in the UI without a reload"; confirmed on a plain managed stack via the detail-page Stop, so it is not the project-name collision of G-18-22-status).

<objective>
Make the live container state follow Docker's event order: decode the event stream line by line, handle one compose project's events strictly in order, and stop subscribing to kill.

Purpose: `docker stop` emits kill, die and stop within milliseconds. `StatePoller` parses each stream chunk as one JSON value and handles every event fire-and-forget, so (a) a chunk carrying several events, or half of one, is dropped, and (b) the kill handler, which inspects a container that is still running, can finish after the die and stop handlers and leave the service running and the stack RUNNING in the database and in the last SSE message until the 60 s reconcile or a reload. This plan reuses the existing `withKeyedLock` (lib/keyed-mutex.ts) for per-project ordering, adds a small buffered decoder in `lib/`, runs reconcile per project under the same key, and drops kill from the filter.
Output: `JsonLinesDecoder` with tests, ordered event handling in `StatePoller` with an end-to-end stream test, and the narrowed event filter.

Out of scope: matching containers to stacks by compose directory (plan 18-25 changes `handleEvent` and `reconcile` after this plan), client SSE handling (the detail page already applies container_state events and refetches after actions), and StackService.stopStack's status ordering.
</objective>
