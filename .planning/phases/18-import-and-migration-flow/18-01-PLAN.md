**GitHub issues:** [#13 Hide Docktor's own stack from "Import existing stack"](https://github.com/docktor-app/docktor/issues/13) (STK-03, implemented here) and [#72 Migration dialog: real diff, explicit backup, stop old stack](https://github.com/docktor-app/docktor/issues/72) (this plan's Task 3 protects #72's `pre-migration-backup/` location; the rest of #72 is plans 18-02..18-05). Issue #13's opt-in read-only display of Docktor's own stack is a deferred idea and is NOT built here.

<objective>
Stop the brownfield scan from offering Docktor's own stack. Per D-01, Docktor inspects its own container at scan time, reads the Compose `config_files` label (host-side, comma-separated, absolute; `working_dir` resolves any relative entry) and maps each host path to the path visible inside the container through the container's own bind mounts (production mounts host `/` at `/host`; `DOCKTOR_STACKS_HOST_DIR` deployments mount identical paths). Any scanned compose path equal to one of those candidates is dropped. Per D-02 the lookup fails open: if anything is unknown, every stack is listed and no heuristic is tried. Per D-03 the filter sits in `OnboardingService.scan`, which both `routes/setup.ts` and `routes/imports.ts` already call, so both get identical behaviour without touching the routes.

Purpose: users importing existing stacks are never offered (and cannot accidentally migrate) the stack that runs Docktor itself.
Output: a pure domain module, a narrow port, a fail-open Docker adapter, the scan filter, and a scanner ignore entry for the backup directory plan 18-03 creates.
</objective>
