**GitHub issue:** [#76 Don't warn about port conflicts for ports the stack itself is using](https://github.com/docktor-app/docktor/issues/76) (STK-01, STK-02). Issue #21 (pre-deploy conflict detection as a feature) is out of scope.

<objective>
Stop the deploy-time port check from flagging a stack's own ports. On redeploy, the stack's own containers are already running, so Docker's userland proxy (`docker-proxy`) listens on every published host port. Tiers 1 and 2 of `resolvePortConflicts` already skip the deploying stack, but tier 3 (listening sockets) has no self-exclusion and reports `docker-proxy` as a conflicting process. Per D-06, the stack's own listening sockets are recognised through its own running containers (compose project = stack id): tier-3 listeners whose (port, protocol) pair one of those containers publishes are dropped. Real conflicts from other stacks, other containers and other processes keep reporting the named holder.

Purpose: no false warning on every successful redeploy, without hiding genuine conflicts.
Output: a pure-domain change in `server/src/domain/port-conflicts.ts` (Claude's discretion per CONTEXT: kept in the pure domain function so `PortConflictService` stays unchanged and the rule is unit-testable), plus tests at domain, service and preflight level.
</objective>
