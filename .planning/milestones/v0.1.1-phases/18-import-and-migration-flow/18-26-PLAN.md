**GitHub issues:** [#72 Migration dialog: real diff, explicit backup, stop old stack](https://github.com/docktor-app/docktor/issues/72) (MIG-04: "so the new draft stack does not run alongside it"). Gap closure round 3 for **18-UAT.md G-18-22-status**, second half: "When stopOldStack is off and the old and new compose project names collide, refuse the migration with a clear message" (**user decision: refuse, not auto-rename**). The matching half is plan 18-25.

<objective>
Refuse a migration that would run the new stack under the compose project name the still-running old stack uses, and make the dialog require the stop in exactly that case.

Purpose: in UAT test 8 the old stack in `.../memos` kept running and the new stack `memos` was deployed under the same project name `memos`. Compose then treats the old containers as the new stack's own (`up` can recreate or remove them) and Docktor's state counts them for the new stack. The user decided this combination is refused. The prediction follows Compose's precedence, because a `name:` in the compose file or `COMPOSE_PROJECT_NAME` in its `.env` is carried into the new stack and collides whatever the stack is called. The preview reports the collision so step 4 shows the switch forced on with the reason, in line with the existing in-place forced stop (18-15).
Output: a pure project-name predictor with tests, the preflight refusal and preview field in `MigrationService`, the shared schema field, and the step-4 UI with tests and fixtures.

Out of scope: auto-renaming the project (rejected by the user), container matching (18-25), projects started with `-p` or a shell `COMPOSE_PROJECT_NAME` that the files do not show (residual, see threat T-18-79), and stacks whose `name:` differs from the stack id (pre-existing, not this gap).
</objective>
