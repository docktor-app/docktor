**GitHub issues:** [#13 Import existing stack](https://github.com/docktor-app/docktor/issues/13). Gap closure for UAT gap **G-18-2** (server half): "the docktor stack was ignored, but the stacks that were already added to docktor are not ignored. I think it is ok to list them, but disable the buttons." The client half (disabled rows with an "Already managed" indicator and a link) is plan 18-13.

<objective>
Tell the scan which discovered stacks Docktor already manages, and refuse adopt or migrate of them on the server.

Root cause (18-UAT G-18-2): neither `OnboardingService.scan` nor the client compares scanned compose files with existing stacks, so managed stacks come back as ordinary importable rows. Locked decision: keep such rows listed with Adopt/Migrate disabled and an "Already managed" indicator; the server rejects adopt/migrate of an already-managed compose path with ConflictError.

Matching rule: a scanned compose file is managed when its directory equals a stack's `hostPath` (both are container-visible paths: Docktor-created and migrated stacks live in the identical-path stacks directory, adopted stacks store the scanned directory). One Docktor stack per directory, so a sibling compose file in a managed directory counts as managed too.

Purpose: users cannot import the same stack twice, and see why.
Output: a pure domain matcher, a repository read, a shared guard, the scan annotation, both refusals, the shared DTO field and updated fixtures.
</objective>
