**Implements:** UAT gap **G-15-14** ("After startup, a single sign-in lands the user in the app and keeps them signed in") in the sign-in flow delivered for [docktor-app/docktor#45](https://github.com/docktor-app/docktor/issues/45) (login second step, D-04). Diagnosis: `.planning/debug/double-login-after-startup.md`.

<objective>
Make one sign-in enough. After `await signIn.email()` / `await twoFactor.verifyTotp()` / `await twoFactor.verifyBackupCode()` resolve, better-auth only refreshes its `useSession` store about 10 ms later (a deferred `setTimeout` in its client proxy). LoginForm navigates to `/` immediately, so ProtectedRoute reads the stale signed-out value `{data: null, isPending: false}` left behind by the user's earlier signed-out visit to `/` and redirects back to `/login`. The fix: a `refreshSession()` helper that awaits the store's own refetch, called before every navigation that follows a sign-in.

Purpose: UAT test 14 (and test 4) failed with "I had to login twice". This is not a Phase 15 regression, but the 2FA sign-in step built in 15-03 has the same race, and the existing e2e journeys start at `/login`, so they never prime the stale value and could not catch it.

Output: `refreshSession()` in `client/src/lib/auth-client.ts`; LoginForm with one `completeSignIn` path; TwoFactorStep awaiting `onSuccess`; setup-wizard auto-login hardened; unit tests asserting refresh-before-navigate plus a contract test against the real better-auth client; Playwright journeys that start signed out at `/` for password and TOTP sign-in.

Not changed: `client/src/components/domain/auth/protected-route.tsx` (its pending/no-session logic is correct once the store is fresh), and `client/src/routes/auth/components/signup-form.tsx`. The sign-up success path cannot run in production: the server rejects `/sign-up/email` once any user exists (server/src/lib/auth.ts before-hook), and FirstRunGate sends a first-run instance to `/setup`.
</objective>

better-auth 1.4.18 client facts (verified in the published dist, client/config.mjs, client/query.mjs, client/proxy.mjs, client/react/index.d.mts):
- `authClient.$store.atoms.session` is a nanostores atom. Its value is `{data, error, isPending, isRefetching, refetch}`. `refetch(queryParams?)` issues GET `/api/auth/get-session`, writes the result (or the error) into the atom, and returns a `Promise<void>` that ALWAYS resolves (its internal promise resolves in a `finally`; it never rejects).
- The react client types `$store.atoms` as `Record<string, WritableAtom<any>>`, so the value read from the atom is any-typed and must be narrowed.
- After a successful `/sign-in/email`, `/sign-up/email` or `/two-factor/*` call, the client toggles `$sessionSignal` inside `setTimeout(..., 10)`; that toggle triggers the store's own refetch. This is the race.
- `createAuthClient` captures the global `fetch` as `customFetchImpl` when the client is created, so a test that wants to stub the network must stub `globalThis.fetch` BEFORE `@/lib/auth-client` is first evaluated.
