  <name>Task 2: Choose the publish gate mechanism (D-06) and whether a 0.x release also moves a bare `0` tag (D-05)</name>
  <decision>How publish.yml waits for CI, and whether v0.x.y releases publish the Docker tag `0`.</decision>
  <context>
    D-06: publishing is a separate workflow gated on CI success, never in parallel with ci.yml. ci.yml has no tag trigger today, and a workflow_run-triggered workflow runs in the default-branch context, so a tag release would not see its own tag (RESEARCH Pitfall 3, Open Question 1). The recommended design makes ci.yml reusable (workflow_call), drops its own push trigger (main's CI then appears inside the "Publish" run; PR checks keep their names), and publish.yml runs `ci` then `publish (needs: ci)`. It is testable from the feature branch with a release-candidate tag (16-09) before anything reaches main.
    D-05 (costly: tag semantics become part of users' compose files) says a release vX.Y.Z publishes X.Y.Z, X.Y, X and latest. For v0.1.0, X is `0`; docker/metadata-action's docs recommend not generating the major tag for major version zero, because 0.x releases may break compatibility and users pinning `:0` would silently receive them (RESEARCH Pitfall 7, Assumption A1). Suppressing it deviates from D-05's literal text only while the major version is 0; from v1.0.0 on, `1` is published.
  </context>
  <options>
