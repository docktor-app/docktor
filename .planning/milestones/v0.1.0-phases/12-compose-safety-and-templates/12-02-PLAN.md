**Implements:** [docktor-app/docktor#20](https://github.com/docktor-app/docktor/issues/20) — decision D-12 (rule registry) and the data side of D-10/D-11.

<objective>
Build the Strategy-pattern compose-check engine (D-12) as a dedicated TDD plan: six built-in rules behind one `Rule` interface, a hardcoded registry, and a `ComposeRuleEngine` behind an application port that parses compose YAML (anchors/merge keys resolved), filters rules by `configurable` + enabled set, and attaches the line number of each finding for in-context display. Task 1 is the thin tracer through every engine layer (port types → rule → registry → engine → line location) with one rule (`privileged`); Task 2 adds the remaining five rules, the ComposeAnalyzer extensions they need, and a registry/settings consistency guard.

Purpose: issue #20's checks are pure business logic with defined I/O (TDD candidates); plans 12-05 (review dialog + create enforcement) and 12-08 (deploy-time re-check, D-09) consume this engine unchanged.
Output: `ComposeRuleEngine` + six rules + shared rule-id/settings schema.
</objective>

## Planning notes

- This is the phase's dedicated TDD plan for pure business rules (TDD-candidate guidance: "validation rules" with defined I/O). Its first task is still the thin tracer through all engine layers; the user-facing end-to-end proof of #20 is plan 12-05's tracer.
- Severity names are `"danger"` (always-on, red tone, D-11) and `"warning"` (configurable, yellow tone). PATTERNS' draft name `"blocking-style"` is deliberately not used — nothing in this phase blocks (#20 "all checks warn, none block").
- Rule ids (camelCase, used as Setting keys by 12-05 and as the client label map key): `privileged`, `dockerSocket`, `bindOutsideStack`, `namedVolume`, `inlineEnv`, `missingEnvFile`.
- The shared constants live in `shared/src/validation/settings.ts` (not a new shared file) so this plan does not touch `shared/src/validation/index.ts`, which plan 12-04 edits in the same wave.

<assumption_delta_decision>
Signal 2 (chosen — "configurable" checks, D-10/D-12): **promote.** `configurable: boolean` is declared on every `Rule` (always-on rules set it to `false`); `ComposeRuleEngine.evaluate` applies one filter — `!rule.configurable || enabled.has(rule.id)` — to all rules. A consistency test pins `ruleDescriptors.filter(configurable)` to `CONFIGURABLE_COMPOSE_RULE_IDS` so a future configurable rule cannot ship without its settings key.
</assumption_delta_decision>
