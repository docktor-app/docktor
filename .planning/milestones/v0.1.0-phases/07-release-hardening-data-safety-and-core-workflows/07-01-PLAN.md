<objective>
Close the last silent-data-loss gap in the Docker-outside-of-Docker stacks-directory chain: `ensureStacksDir()`'s `mkdir` succeeding does not prove the stacks bind mount actually attached, so a container whose volume never attached boots cleanly, accepts stacks, and discards every compose file, `.env`, and relative bind-mount payload the next time the container is recreated.

Purpose: Docktor is a backup tool for self-hosters. A backup tool that silently loses the data it manages is worse than one that refuses to start. This phase makes non-persistent stacks storage a loud boot failure instead of an invisible time bomb.

Output: a mountinfo-backed persistence check in `server/src/lib/stacks-dir.ts`, wired into the existing fail-fast boot sequence in `server/src/index.ts`, unit-tested against fixture mountinfo content, and documented for operators in `docs/deployment.md`.
</objective>

**No CONTEXT.md exists** (discuss-phase deliberately skipped — single well-documented bug, no open design decisions). The design choices below are the planner's discretion, recorded here so the executor does not re-litigate them:

- **PD-1 (naming):** `assertStacksDirIsMounted()` (public, async, throws) + `findMountEntryForPath()` (pure, exported for tests). Mirrors the existing `assertStacksDirMatchesHost()` naming and export shape in the same module.
- **PD-2 (signal):** match the **deepest mountinfo entry covering the path** (the path itself or an ancestor directory), then judge that entry's filesystem type — instead of research's "exact match only". Exact-match-only would hard-fail a perfectly persistent layout where the operator mounts a parent directory (e.g. `/opt/docktor` mounted, `DOCKTOR_STACKS_DIR=/opt/docktor/stacks`). Deepest-ancestor + filesystem type is correct in both the container case (nearest covering mount is `/`, type `overlay` -> ephemeral) and the bare-metal case (nearest covering mount is `/`, type `ext4` -> persistent).
- **PD-3 (fail only on positive evidence):** the check throws only when it has positive evidence of ephemerality. Unreadable `/proc/self/mountinfo`, or no covering entry at all, warns and continues. This is the mitigation for research Assumption A1 (a hardened runtime masking `/proc` must never brick a working deployment).
- **PD-4 (research Open Question 1, resolved):** the check is **not** gated on `DOCKTOR_STACKS_HOST_DIR` being set, because PD-2's filesystem-type rule already gives the right answer on bare metal without any gating. `DOCKTOR_STACKS_HOST_DIR` is used only as a secondary signal in Task 2 (container root covering the stacks path in a deployment that has declared itself containerized).
- **PD-5 (testability):** `assertStacksDirIsMounted()` takes an optional reader parameter defaulting to reading `/proc/self/mountinfo`, so unit tests inject fixture content instead of mocking `node:fs/promises`. Module-level mocking is specifically unsafe here: `server/test/unit/lib/stacks-dir.test.ts` imports `mkdir`/`mkdtemp`/`rm`/`stat`/`writeFile` from the same module for its real-filesystem `ensureStacksDir` tests, which a `vi.mock("node:fs/promises")` would break. `server/src/index.ts` calls the function with no argument and is unaffected.
</planning_notes>
