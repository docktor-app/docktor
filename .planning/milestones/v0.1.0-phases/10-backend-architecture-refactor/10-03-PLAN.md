<objective>
Build the domain-event bus primitive: the event catalog, the port interface, and an in-memory synchronous implementation whose defining property is **per-subscriber failure isolation**.

This plan ships the mechanism only. No existing call site is migrated onto it — plans 10-11 (status and configuration broadcasts), 10-12 (notifications) and 10-13 (the audit trail) do that, one of D-15's three side-effect categories each. Shipping the primitive separately means the phase's single highest-risk implementation detail gets its own dedicated test before three migration waves depend on it.

Purpose: 10-RESEARCH.md falsified live this session that Node's `EventEmitter.emit()` isolates listeners — a throwing listener aborts the dispatch and every listener registered after it never runs. D-17 requires the opposite. The existing `StateBroadcaster` uses exactly the naive pass-through pattern, so copying it would ship the defect. The isolation test is therefore the acceptance test for the whole event-bus half of this phase.
Output: `server/src/domain/events.ts`, `server/src/application/ports/event-bus-port.ts`, `server/src/infrastructure/event-bus.ts`, and an isolation test suite.
</objective>

  <name>Task 2: InMemoryEventBus with per-subscriber failure isolation</name>
  <files>server/src/infrastructure/event-bus.ts, server/test/unit/infrastructure/event-bus.test.ts</files>
  <behavior>
    - Two subscribers on one event, the first throws synchronously: the second still receives the payload, and `emit` returns normally to its caller.
    - Two subscribers on one event, the first returns a rejected promise: the second still receives the payload, `emit` returns normally, and the process records no unhandled rejection.
    - A throwing subscriber produces exactly one error log naming the event key, so a suppressed side effect is diagnosable.
    - Subscribers registered for a different event key are not invoked.
    - The unsubscribe function returned by `subscribe` removes only that handler; a second handler registered for the same key still runs afterwards.
    - Calling the unsubscribe function twice is a no-op and does not remove another handler.
    - Emitting an event with zero subscribers is a no-op that does not throw.
    - Subscribers run in registration order.
    - Payload identity is preserved: the object handed to `emit` is the object each subscriber receives.
  </behavior>

  </read_first>
  <action>
Create `server/src/infrastructure/event-bus.ts` with `export class InMemoryEventBus implements EventBusPort`.

Back it with a private Node event emitter instance for listener storage and removal only — the emitter's own dispatch is not used. Call `setMaxListeners(100)` in the constructor, matching the `StateBroadcaster` precedent, with a comment stating that this bus accumulates more heterogeneous subscribers per event than the broadcaster's single SSE channel did.

`emit` iterates the raw listeners registered for the key and invokes each inside its own `try`/`catch`. A thrown error is caught and logged with the event key and the error; dispatch then continues to the next listener. If a listener returns a thenable, attach a rejection handler that logs in the same shape — an async subscriber's rejection must be captured at the boundary, never escape as an unhandled rejection. `emit` itself returns `void` and, by construction, has no path that propagates a subscriber error to its caller.

Use the raw-listener accessor rather than the plain listener accessor, so a future `subscribe` implementation that wraps handlers stays observable through the same loop.

`subscribe` registers the handler on the private emitter and returns a function that removes exactly that handler.

Export a module-level `domainEventBus` singleton at the bottom of the file, following the convention every other infrastructure module uses. It has no subscribers until plan 10-11 wires the first one in the composition root.

Write `server/test/unit/infrastructure/event-bus.test.ts` covering every case in this task's `<behavior>` block. The two isolation cases are the acceptance test for D-17 and must assert the *second* subscriber's side effect actually happened, not merely that `emit` did not throw — 10-RESEARCH.md's falsification run shows a naive implementation also does not throw at the call site when the caller wraps it, so "did not throw" alone does not discriminate. For the async-rejection case, assert the rejection was handled rather than merely not observed: register a `process` unhandled-rejection listener for the duration of the case, or await a microtask turn and assert the error log fired.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| publisher -> bus -> subscriber | A new in-process fan-out point where one subscriber's failure can affect another subscriber's side effect, including a security-relevant audit-trail write |
| bus -> log sink | Event payloads reach `console` in the error path; payloads will later carry notification text and stack identifiers |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-05 | Repudiation | `InMemoryEventBus.emit` dispatch loop | high | mitigate | Per-listener `try`/`catch` dispatch so a failing notification subscriber cannot suppress the `StackEvent` audit-trail subscriber registered after it; acceptance criteria require the isolation to be proven by a test that asserts the second subscriber's side effect, and require the naive delegation to demonstrably fail that test |
| T-10-06 | Denial of Service | `emit` called from a status-transition choke point | high | mitigate | `emit` returns `void` synchronously and has no path that propagates a subscriber error to its caller, so a subscriber can never strand a stack in a transitional status — the exact bug class plan 05.1-02 fixed. The `<behavior>` block asserts `emit` returns normally with a throwing subscriber registered |
| T-10-09 | Information Disclosure | bus error logging | medium | mitigate | The error log names the event key and the error; the payload is not logged. Once plan 10-12 adds notification payloads carrying user-facing message text, this keeps recipient addresses and message bodies out of the log |
| T-10-10 | Denial of Service | unbounded subscriber growth | low | accept | `setMaxListeners(100)` matches the existing `StateBroadcaster` precedent and exceeding it warns rather than fails. Subscribers are registered once at composition-root wiring time, not per request, so growth is bounded by source code |
| T-10-SC | Tampering | npm/pip/cargo installs | low | accept | No package is installed; D-16 explicitly rejects a pub/sub library and 10-RESEARCH.md records zero new npm dependencies phase-wide |
</threat_model>
