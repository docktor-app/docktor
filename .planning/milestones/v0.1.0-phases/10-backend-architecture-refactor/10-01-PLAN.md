<objective>
Establish the phase's layering contract by proving it end-to-end on one real, already-identified violation: `application/notification-service.ts` reaching past its layer into Prisma (D-10) and into the mail transport library directly (D-07).

This is the phase's **tracer slice**. It wires one capability — "send a notification email" — through every layer the phase restructures (composition root -> application service -> port interface -> infrastructure adapter, and application service -> port -> repository -> Prisma) and leaves the conventions every later wave copies: where ports live, how repositories are published, and an automated architecture guard that makes a regression fail a test instead of a review.

Purpose: D-05 names layering as the foundation the event bus and job work build on. Every later plan in this phase extends one of the three artifacts created here (`application/ports/`, `repositories/index.ts`, `test/unit/architecture/layering.test.ts`).
Output: `repositories/index.ts`, `repositories/user-repository.ts`, `application/ports/smtp-client-port.ts`, `infrastructure/smtp-client.ts`, an architecture fitness test, and a `NotificationService` with no infrastructure or data-access imports of its own.

<plan_decisions>
Decisions taken during planning that bind every plan in this phase. Recorded here (the wave-1 plan) because later plans inherit them.

- **PD-1 — Port interfaces live in `server/src/application/ports/`, one file per port.** 10-RESEARCH.md Assumption A1: all infrastructure dependencies are consumed by `application/` services, never by `domain/` code, and `domain/` must stay free of I/O-shaped types. D-07 says "application/domain" without picking one; this phase picks `application/ports/` and applies it consistently.
- **PD-2 — D-07 is read broadly: every class under `server/src/infrastructure/` gets a named port.** D-07's own wording is "Interface **every** infrastructure dependency, even single-implementation ones", with four named as examples; D-01 asks for "stricter DI conventions **across the board**" and D-06 commits to full scope. Narrowing to the four named classes would be a descope this planner has no authority to make. The four named ones land in waves 1-2 (plans 10-01 and 10-02); the remaining six in wave 3 (plan 10-05).
- **PD-3 — The `Pick<ConcreteClass, "method">` structural-typing style is replaced by named ports wherever a port exists.** 10-RESEARCH.md Anti-Patterns: `Pick<>` gives the same testability but does not document the contract independently of the concrete class.
- **PD-4 — Route-layer violations are in scope.** `CLAUDE.md` states "Routes **only** call application services"; 10-CONTEXT.md's scouting section explicitly flags the three largest route files for the layering pass; 10-RESEARCH.md Open Question 3 found `routes/stacks.ts` importing a repository directly. These are the same defect class as D-10 and are planned in waves 5-7 (plans 10-08, 10-09 and 10-10), not silently deferred.
- **PD-5 — No fallback or descope path is planned anywhere in this phase (D-06).** If a task proves unworkable during execution, the executor halts and reports; it does not ship a reduced version. No plan in this phase contains "v1", "simplified", "for now", or "later phase" language about its own scope.
</plan_decisions>
