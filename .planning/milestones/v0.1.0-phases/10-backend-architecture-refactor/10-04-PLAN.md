<objective>
Build the job abstraction and registry as a standalone mechanism: a `Job` lifecycle contract, two base classes for the two job kinds D-13 names, and a registry that starts, stops and health-tracks registered jobs with per-job failure isolation on both sides of the lifecycle.

No existing job is migrated by this plan — plan 10-07 does that and rewires `jobs/index.ts`. Shipping the mechanism first means the base classes and the registry each get their own tests against synthetic jobs, rather than being validated only indirectly through seven real jobs with real Docker, chokidar and database dependencies.

Purpose: `jobs/index.ts` today duplicates a try/catch wrapper seven times for starts and applies none at all to stops (10-RESEARCH.md Pitfall 4 — a throwing `stop()` aborts the remaining stops and can leak a running cron task or event stream on shutdown). D-14 replaces that duplication with a registry that also records the health state Phase 14 can later build on.
Output: `server/src/jobs/job.ts`, `server/src/jobs/job-registry.ts` and their tests.
</objective>

<plan_decisions>
- **PD-6 — Taxonomy resolution for the two jobs that fit neither kind** (10-RESEARCH.md Open Question 2, Assumption A2). `Job` is the registry-facing lifecycle contract; `IntervalJob` and `WatcherJob` are base classes that make implementing it easy for the two common shapes, not an exhaustive partition.
  - `NotificationWatcher` (no cron call anywhere in its file) is a **watcher** whose reconcile schedule is `null`. It has genuinely nothing to reconcile against — a missed in-process broadcast leaves no queryable drift, unlike a stale file hash or container state. The base class therefore treats the reconcile schedule as optional rather than forcing a no-op tick.
  - `BackupScheduler` (a runtime-managed `Map` of one cron task per stack, upserted from a route) is kind **dynamic** and implements `Job` directly, keeping its per-stack task map internal. Its `lastRun` is reported at the scheduler level (last time any per-stack task fired), which is the only honest reading of a single field for an N-task job.
  - Reversibility: reversible — a later phase can promote `dynamic` to its own base class without touching the registry contract.
- **PD-7 — `"BackupRecovery"` is not a Job.** `jobs/index.ts` currently routes `backupService.recoverInProgressBackups()` through the same start wrapper as the seven real jobs, but it is a one-shot startup call with no `stop()` and no schedule. It stays a pre-start hook of the registry (isolated the same way, excluded from health tracking), rather than being modelled as a job with permanently meaningless health fields. Implemented in plan 10-07.
</plan_decisions>

  <name>Task 1: The Job contract and the IntervalJob / WatcherJob base classes</name>
  <files>server/src/jobs/job.ts, server/test/unit/jobs/job.test.ts</files>
  <behavior>
    - An interval job's `start()` schedules its run body on the cron expression the subclass declares, and `stop()` cancels that schedule and clears the handle.
    - An interval job declaring immediate-run-on-start invokes its run body once during `start()`, before any scheduled tick.
    - An interval job that does not declare immediate-run-on-start does not invoke its run body during `start()`.
    - A run body that throws is caught inside the base class, reported to the health reporter as an error, and does not propagate out of the scheduled callback.
    - A successful run body is reported to the health reporter as a run, with no error.
    - A watcher job's `start()` attaches its event source first and then schedules the reconcile tick, in that order.
    - A watcher job whose reconcile schedule is `null` attaches its event source and schedules nothing — no cron handle is created.
    - A watcher job's `stop()` detaches the event source and cancels the reconcile schedule, and does both even when detaching throws.
    - Calling `stop()` on a job that was never started is a no-op and does not throw.
    - Calling `start()` twice does not leave a leaked, uncancellable schedule from the first call.
  </behavior>

Create `server/src/jobs/job.ts` containing the lifecycle contract and the two base classes. Keep it dependency-light: it imports the cron package and nothing else from `server/src/`.

Declare:
- `JobKind` — a union of three literals: the interval kind, the watcher kind, and the dynamic kind (PD-6's escape hatch for a job that manages its own set of schedules).
- `JobHealthReporter` — a two-member interface (`recordRun(jobName)`, `recordError(jobName, error)`), so a job reports outcomes without importing the registry. Keeping the arrow pointing this way is what lets `job.test.ts` assert reporting with a plain object.
- `Job` — `readonly name: string`, `readonly kind: JobKind`, `start(): Promise<void> | void`, `stop(): Promise<void> | void`, and `setHealthReporter(reporter: JobHealthReporter): void`. `start`/`stop` are allowed to be async because `FileWatcher.stop()` already awaits a close promise.
- `abstract class IntervalJob implements Job` — kind fixed to the interval literal. Subclass supplies `name`, a cron expression, a `protected abstract run(): Promise<void> | void` body, and a flag for whether `start()` fires one immediate run before scheduling (the disk-checker shape). The base class owns the schedule handle, the schedule/cancel calls, the try/catch around every invocation of `run()`, and the health reporting.
- `abstract class WatcherJob implements Job` — kind fixed to the watcher literal. Subclass supplies `name`, a `protected abstract attach(): Promise<void> | void`, a `protected abstract detach(): Promise<void> | void`, a `protected abstract reconcile(): Promise<void> | void`, and a reconcile cron expression that may be `null`. `start()` attaches first, then schedules the reconcile only when the expression is non-null. `stop()` detaches and cancels, with the detach wrapped so a failing detach still cancels the schedule.

Both base classes route every invocation of the subclass body through one private helper that try/catches, logs with the job name in the existing `[JobName] ...` log prefix style the current job files use, and reports to the health reporter when one is set. A job with no reporter set behaves identically minus the reporting — the base classes must be usable standalone in tests.

The cron expression is read from the subclass rather than passed to a constructor, so each concrete job keeps its schedule literal next to its own code where it is reviewable, exactly as today.

Write `server/test/unit/jobs/job.test.ts` against **synthetic** subclasses defined inside the test file — never against a real job. Mock the cron package the same way the existing job tests do, capturing the scheduled callback so a tick can be invoked deterministically. Cover every case in this task's `<behavior>` block.

<task type="auto" tdd="true">
  <name>Task 2: JobRegistry with per-job health tracking and two-sided failure isolation</name>
  <files>server/src/jobs/job-registry.ts, server/test/unit/jobs/job-registry.test.ts</files>
  <behavior>
    - `startAll()` starts every registered job, in registration order.
    - A job whose `start()` throws is logged, recorded as failed with its error, and every subsequent job still starts.
    - A job whose `start()` rejects asynchronously is handled identically to a synchronous throw.
    - `stopAll()` stops every registered job even when an earlier job's `stop()` throws or rejects.
    - After a successful `startAll()`, each job's health status reads as running and carries a start timestamp.
    - After `stopAll()`, each job's health status reads as stopped.
    - A job that reports a run through the health reporter has its last-run timestamp advanced and its last error left untouched.
    - A job that reports an error has its last error and last-error timestamp recorded while its status stays running — a failing tick is not a stopped job.
    - Registering two jobs with the same name is rejected rather than silently overwriting the first.
    - `register()` gives the job a health reporter, so an unregistered job never writes into the registry.
    - Reading health returns a snapshot the caller cannot mutate into the registry's own state.
  </behavior>

Declare `JobHealth` as a readonly record per job: job name, kind, a status union (stopped / running / failed-to-start), last-started timestamp, last-successful-run timestamp, last error (the error's message, not the error object — a stored `Error` keeps a stack and potentially a `cause` chain alive for the process lifetime, and the message is what a future health view would render), and last-error timestamp. Nullable where not yet observed.

Declare `export class JobRegistry implements JobHealthReporter` with:
- `register(job: Job): void` — rejects a duplicate name with the codebase's typed `ConflictError` from `lib/errors.ts` rather than a bare `Error`, seeds the job's health entry in the stopped state, and calls `job.setHealthReporter(this)`.
- `startAll(): Promise<void>` — awaits each job's `start()` **sequentially in registration order**, each inside its own try/catch. This preserves the existing cold-start contract: jobs start one at a time and one failure never blocks another or the HTTP server. On success mark running and stamp last-started; on failure log with the job's name and mark failed-to-start with the error message.
- `stopAll(): Promise<void>` — the same sequential, individually-isolated treatment applied to `stop()`, closing the gap where a throwing stop aborted the remaining stops.
- `recordRun(jobName)` / `recordError(jobName, error)` — the `JobHealthReporter` implementation. An error advances last-error without changing a running job's status.
- `health(): JobHealth[]` (or an equivalent snapshot accessor) returning copies, so a caller cannot reach into the registry's map.

Export a module-level `jobRegistry` singleton at the bottom of the file. It has no registered jobs until plan 10-07.

This is internal state only (D-14). Do not add a route, a Fastify decorator, an SSE event or a settings key that surfaces it — that is Phase 14's work, and this plan's groundwork is complete without it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| job body -> registry health state | Arbitrary error values from Docker, restic, SMTP and filesystem failures are captured into long-lived in-process state |
| registry -> (future) health surface | D-14 defers the surface, but anything stored now becomes what a Phase 14 view would render |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-11 | Information Disclosure | `JobHealth.lastError` | medium | mitigate | Store the error's message string only — never the error object, its `cause` chain, or any config/env object a job was operating on. Restic and SMTP errors are the realistic carriers of credentials and absolute host paths, and 04-backup-restore already surfaces restic stderr elsewhere; keeping this field to a message is what stops a later health view leaking more than intended |
| T-10-12 | Information Disclosure | premature health endpoint | medium | mitigate | D-14 scopes the health state as internal. Acceptance criteria assert no reference to the registry exists under `server/src/routes/` or in `app.ts`, so no unauthenticated surface can appear by accident in this phase |
| T-10-13 | Denial of Service | `startAll()` cold-start path | high | mitigate | Sequential, individually try/caught starts preserve the exact contract a cold docker-compose start depends on (STATE.md: an unguarded `startJobs()` once took down the whole process on a database that was not ready). A concurrency change is named as a prohibition and asserted by a registration-order test |
| T-10-14 | Denial of Service | shutdown leak | medium | mitigate | `stopAll()` gains the same per-job isolation `startAll()` already had, so a throwing `stop()` can no longer leave later jobs' cron tasks or event streams running (10-RESEARCH.md Pitfall 4) |
| T-10-SC | Tampering | npm/pip/cargo installs | low | accept | No package is installed; D-12 keeps the already-installed cron package |
</threat_model>
