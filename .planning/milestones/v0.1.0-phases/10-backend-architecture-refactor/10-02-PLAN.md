<objective>
Declare and implement named port interfaces for the four infrastructure dependencies D-07 names explicitly, continuing the convention plan 10-01 established with `SmtpClientPort`.

This plan is **declaration only** — it creates the port files and makes each concrete class declare `implements`. Consumers keep compiling unchanged (a class that implements an interface is still assignable to a parameter typed as the class). Switching consumers over to the port types happens in plan 10-06 (application services) and 10-07 (jobs), which own those files.

Purpose: D-07 asks for named interfaces rather than the codebase's current mix of concrete-class types and `Pick<ConcreteClass, "...">` structural types (PD-3). The `implements` clause is the load-bearing part: it turns "the port describes the class" from a comment into a compiler-checked fact.
Output: four port files under `server/src/application/ports/`, four infrastructure classes carrying an `implements` clause.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| application -> Docker socket | `DockerExecutor` and `DockerodeClient` are the process's only Docker Engine access; their argv/API calls cross the boundary |
| application -> shell / child process | `DockerExecutor` and `ResticExecutor` build argument vectors for spawned binaries |
| application -> host filesystem | `StackFilesystem` resolves and writes paths under the stacks directory |
