<objective>
Make `server/src/routes/stacks.ts` obey the rule `CLAUDE.md` already states — routes only call application services — by moving its four cross-layer reaches behind services, and collapse the duplicated image-reference builder into one domain function on the way.

`routes/stacks.ts` today imports the database client, a repository, an infrastructure client and a job module. Three of those are exactly the defect class D-10 names in the application layer; 10-RESEARCH.md Open Question 3 found the repository one independently. PD-4 (recorded in `10-01-PLAN.md`) puts them in scope: D-01 asks for a full restructure, and 10-CONTEXT.md's scouting section flags this file by name for the layering pass.

Purpose: these routes are the phase's hardest no-behaviour-change constraint — every one of them is on the API contract the phase boundary freezes, and the log route is the one with a real disconnect-leak history.
Output: a `routes/stacks.ts` with no cross-layer imports, a new `LogService`, and one image-reference builder instead of two.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> HTTP route | Client-supplied stack ids and service names select which container's logs are streamed |
| application -> Docker socket | Opening a container log stream is direct Docker Engine access |
| server -> client (SSE) | A long-lived stream whose lifetime must be bounded by the client connection |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-25 | Elevation of Privilege | service-name scoping in the upgrade-candidate and log endpoints | high | mitigate | The scoping (resolve the service from the addressed stack's own service list, raise not-found otherwise) moves unchanged and in the same order, before any container is addressed; Task 2's and Task 3's acceptance criteria each require a test case for an unknown or out-of-stack service name |
| T-10-26 | Denial of Service | log-stream leak on client disconnect | high | mitigate | The disconnect handler stays in the route, registered on the same request event over the same stream set; the executor records the before/after handler body, and the leak's history is in the read-first list so it cannot be treated as incidental |
| T-10-27 | Spoofing | image-reference lookup key | medium | mitigate | Consolidating the two builders must not change what either returns for any covered input; the surviving implementation is the one whose output is the persisted lookup key, and every parity-test input case is preserved against it |
| T-10-28 | Information Disclosure | response-shape drift | medium | mitigate | Before/after response shapes for all three endpoints are recorded in the summary and asserted identical — the phase boundary forbids any API contract change, including a field that quietly appears or disappears |
| T-10-04 | Tampering | `requireAuth` preHandlers | high | mitigate | This plan edits handler bodies only; no route registration, schema or preHandler is touched. The summary records that the preHandler list on every touched route is unchanged |
| T-10-SC | Tampering | npm/pip/cargo installs | low | accept | No package is installed |
</threat_model>
