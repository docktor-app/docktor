<objective>
Close G-06-3: assigning a domain with an invalid hostname returned 201 instead of 400.

The hostname regex, `assignDomainSchema` and `routes/proxy.ts` were each independently
proven correct during the debug session — nothing in this phase's application code is
wrong. What is wrong is the monorepo's build pipeline: `@docktor/server` imports
`assignDomainSchema` from `@docktor/shared`, which resolves through
`shared/package.json`'s `"main": "dist/index.js"` — a compiled, gitignored artifact that
**nothing rebuilds before server tests run**. Only the root `build`/`build:server`
scripts do. A stale `shared/dist` therefore validates request bodies against an older,
more permissive schema, and the debug session reproduced the exact 201 by removing only
the `.regex(...)` call from the compiled file.

Purpose: make that class of failure impossible through the normal entry points, and
loud rather than silent everywhere else. A stale compiled dependency that quietly
disables a security boundary (T-06-02 domain injection) and costs a full debugging
session to find is exactly the design debt CLAUDE.md says not to leave behind.

Output: every test and dev entry point that consumes `@docktor/shared` builds it first;
a database-free regression test that pins the 400; and a parity test that fails in under
a second, with an actionable message, whenever the compiled artifact disagrees with its
source.
</objective>

<planner_decisions>
- **`pretest` hooks — REJECTED, empirically.** Yarn Berry does not run arbitrary
  `pre`/`post` lifecycle scripts. Verified in a throwaway `yarn@4.13.0` project with a
  `pretest` and a `test` script: `yarn run test` printed only the `test` output. A
  `pretest` entry would have looked like a fix and silently never run — the same class of
  invisible failure this plan exists to remove. The build is therefore chained
  explicitly with `&&` inside each script. Yarn runs scripts through its own portable
  shell, so `&&` behaves identically on Windows, and Yarn appends any extra CLI arguments
  to the end of the expanded command, so
  `yarn workspace @docktor/server test:integration test/integration/proxy.test.ts` still
  lands the path on the `vitest` invocation.
- **A vitest alias mapping `@docktor/shared` to `shared/src` — REJECTED.** It would make
  tests immune to staleness by construction, but it would also mean no test ever
  exercises the artifact the running server actually imports, so a broken emit could
  ship green. Keeping the compiled artifact in the test path and *guaranteeing it is
  fresh* preserves fidelity; the parity test below covers the residual risk.
- **`shared`'s `build` script left as `tsc --project tsconfig.json` — deliberate.**
  Probed both modes against a composite project: after a source edit (the realistic
  staleness case) `tsc --project` re-emits correctly; when outputs are deleted while
  `tsconfig.tsbuildinfo` survives, *neither* `tsc --project` nor `tsc --build` re-emits.
  Build mode buys nothing here, so the script is left alone and the residual hole is
  covered by the parity test instead of by a slower `--force` build on every test run.
- **`yarn dev` gets a one-shot build, not a `tsc --watch` process.** Prefixing the
  existing `concurrently` invocation guarantees a fresh `shared` at dev startup — the
  fresh-clone and post-`git pull` cases — without changing the process tree. A watch
  process was considered and dropped: Vite pre-bundles linked workspace dependencies, so
  it would not reliably hot-reload rebuilt `shared` output anyway, and mid-session edits
  to `shared/src` already require a dev restart today.
- **The parity test lives in `server/test/unit/`, not in `shared/`.** The server is the
  workspace whose module resolution was fooled; asserting from inside the server's own
  module context is what proves the guarantee that matters.
</planner_decisions>
