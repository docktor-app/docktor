# Docktor — Claude Code Guidelines

## Project Overview

Docktor is a self-hosting management platform for Docker Compose applications.
It is a **Yarn v4 monorepo** with three workspaces:

| Workspace | Path | Role |
|-----------|------|------|
| `@docktor/shared` | `shared/` | Shared Zod validation schemas and types |
| `@docktor/server` | `server/` | Fastify 5 + Prisma 7 + PostgreSQL backend |
| `@docktor/client` | `client/` | React 19 + Vite 7 + TailwindCSS 4 frontend |

---

## Core Principles

**Software quality is the highest priority.** Favour correctness, clarity, and maintainability over speed of delivery. Every change should leave the codebase in better shape than it was found.

1. **Modular, layered architecture** — respect existing boundaries between layers
2. **Domain-Driven Design (DDD)** — model the domain explicitly; keep business logic in the domain/application layers
3. **Test-Driven Development** — write tests before or alongside implementation; all features must be covered
4. **Strict TypeScript** — no implicit `any`, no unsafe casts; types are documentation
5. **Design patterns** — apply patterns (Repository, State Machine, Factory, Strategy, Observer, etc.) when they fit the use case; never force them
6. **Continuous refactoring** — improve code quality whenever a change touches a module; leave no design debt behind

## Architecture

### Server — Layered DDD

```
routes/          ← HTTP boundary: Zod schema validation, auth middleware, delegates to services
application/     ← Use-case / application services (business operations)
domain/          ← Pure business rules: state machines, invariants, value objects
repositories/    ← Data access abstraction; all Prisma queries live here
infrastructure/  ← External adapters: Docker, filesystem, third-party clients
jobs/            ← Background workers: StatePoller, FileWatcher, UpdateChecker
lib/             ← Technical utilities: auth, errors, DB client, slugify, parsers
```

**Rules:**
- Routes **only** call application services — never touch repositories or Prisma directly
- Services **never** import route types or HTTP concerns
- Domain code is **pure** (no I/O, no Prisma, no Fastify)
- Repositories are the **only** place that touches Prisma
- Dependency injection via **constructor parameters** — keeps units testable in isolation
- Export singleton repository instances from `repositories/index.ts`

### Client — React Component Composition

```
routes/                        ← Page-level route components (React Router v7)
routes/<page>/components/      ← Section components used only by that one page
components/ui/                 ← shadcn/ui primitives — do not modify these files
components/common/             ← Generic, reusable UI components (not domain-aware)
components/domain/             ← Feature-specific, domain-aware components
hooks/                         ← Custom hooks encapsulating data fetching and real-time state
lib/                           ← API clients, HTTP helper, auth client, utilities
```

**Rules:**
- Domain components **import** from `lib/` and `hooks/`; they do **not** fetch data directly
- `components/ui/` files are **generated by shadcn** — do not edit them manually
- Custom hooks are the **single source of truth** for server state; pages compose hooks

### Page Composition

**A page file is an orchestrator, not an implementor.** Its job is to:
1. Call hooks to obtain data
2. Render a `<Page>` shell with header, breadcrumbs, and actions
3. Compose section components — one per logical section of the page

**Target: a page file should not exceed ~80 lines.** If it grows beyond that, extract sections.

**Section component rule:** Every distinct visual/functional section of a page gets its own component file. Co-locate it next to the route file when it is only used by that page:

```
routes/app/stacks/[id].tsx                         ← page: composes sections
routes/app/stacks/components/stack-actions.tsx     ← header action buttons
routes/app/stacks/components/services-tab.tsx      ← Overview > Services card
routes/app/stacks/components/deployments-tab.tsx   ← Overview > Deployments card
routes/app/stacks/components/compose-tab.tsx       ← Compose editor tab
routes/app/stacks/components/environment-tab.tsx   ← Env editor tab
```

If a section component is used by more than one page, promote it to `components/domain/` or `components/common/`.

**Do not define helper components inline in the page file.** Even a small local component like `ServiceStatusBadge` belongs in its own file (in `components/domain/` if domain-aware).

### Reusable UI Components

`components/common/` is for generic components that are **not** tied to any domain concept. They must be reusable across pages without modification. Examples of what belongs here:

- Layout primitives (`Page`, `PageHeader`, `DataTable`)
- Generic empty states, loading skeletons, error boundaries
- Generic stat/metric cards (parameterised by label, value, icon — not hardcoded to "Total Stacks")
- Generic confirmation dialogs, action menus

If a component references domain types (Stack, Service, Deployment…) or domain vocabulary, it goes in `components/domain/`, not `components/common/`.

**Component file checklist before adding to `components/common/`:**
- [ ] Props are generic — no domain-specific prop names or types
- [ ] The component could be dropped into a completely different project and still make sense
- [ ] No direct API calls or hook usage inside the component (accept data via props)

## TypeScript Standards

- `strict: true` is enforced across all workspaces — never disable it
- **No `any`** — use `unknown` and narrow the type, or model the type properly
- **No unchecked casts** — `as SomeType` is only acceptable with a comment explaining why it is safe
- Use `z.infer<typeof schema>` for runtime-validated types (Zod schemas live in `@docktor/shared`)
- Prisma types are the source of truth for database shapes — use generated types, not manual re-declarations
- Use utility types (`Pick<>`, `Omit<>`, `Partial<>`, `Record<>`) rather than duplicating interfaces
- Component props interfaces must be named `<ComponentName>Props` and use `Readonly<Props>` in function signatures
- Use explicit return types on exported functions and public class methods

### Naming Conventions

| Entity | Convention | Example |
|--------|-----------|---------|
| React components | PascalCase | `StackStatusBadge.tsx` |
| Hooks, utilities, API clients | kebab-case | `use-stacks.ts`, `stacks-api.ts` |
| Domain/business files | kebab-case | `stack-status-machine.ts` |
| Classes | PascalCase | `StackRepository` |
| Constants | SCREAMING_SNAKE_CASE | `TRANSITIONAL_STATES` |
| Variables / functions | camelCase | `deployStack()` |
| Prisma models | PascalCase | `Stack`, `Service` |
| Prisma enum values | SCREAMING_SNAKE_CASE | `RUNNING`, `DEPLOYING` |
| Test files | `*.test.ts` / `*.test.tsx` | `stack-service.test.ts` |

## Testing

### Philosophy

- **TDD is the default** — write the test first, then make it pass
- Every new feature and bug fix must have corresponding tests
- Tests must cover both the happy path and edge cases / error paths
- Do **not** test implementation details — test observable behaviour

### Structure

```
server/test/unit/          ← Unit tests for services, domain logic, repositories (mocked deps)
server/test/integration/   ← Integration tests hitting real Fastify + real DB
client/test/unit/          ← Component, hook, and lib unit tests (jsdom / testing-library)
client/test/integration/   ← Playwright E2E tests
```

### Rules

- **Server unit tests**: mock the repository, filesystem, and Docker; test services and domain logic in isolation
- **Server integration tests**: run against a real database (no mocked DB — lessons from past regressions)
- **Client hook tests**: mock `fetch` / API clients; test hook state transitions
- **Client component tests**: use `@testing-library/react`; prefer queries by role / label
- Keep integration tests isolated — each test cleans up its own data
- Coverage is tracked via SonarQube (LCOV reports in `.test/coverage/`) — do not let coverage drop

### Running Tests

```bash
# All workspaces
yarn test

# Server only
yarn workspace @docktor/server test
yarn workspace @docktor/server test:integration

# Client only
yarn workspace @docktor/client test
yarn workspace @docktor/client test:integration  # Playwright
```

## Design Patterns in Use

Apply patterns where they improve clarity — never for their own sake.

| Pattern | Where it is used | When to extend |
|---------|-----------------|----------------|
| **Repository** | `server/repositories/` | Any new data access; never query Prisma outside a repository |
| **State Machine** | `domain/stack-status-machine.ts` | Add new states/transitions here; keep transition logic pure |
| **Service (Application)** | `server/application/` | New use cases; one service per aggregate root |
| **Strategy** | `infrastructure/` adapters | Swap Docker or filesystem implementations |
| **Observer / Pub-Sub** | `StateBroadcaster` + SSE streams | Real-time events to connected clients |
| **Factory** | Fastify plugin factory (`createApp`) | Testable app construction |
| **Decorator** | Fastify hooks (`requireAuth`) | Cross-cutting concerns on routes |
| **Generic Component** | `DataTable<T>` | Reusable UI over typed data |

## Error Handling

### Server

- Throw typed errors from the custom hierarchy — **never** throw raw `Error` in business code:

  ```typescript
  // lib/errors.ts
  AppError       // base, 500
  NotFoundError  // 404
  ConflictError  // 409
  BadRequestError // 400
  ```

- Repository `findByIdOrThrow()` methods throw `NotFoundError`; callers need not re-check
- The global Fastify error handler in `app.ts` converts `AppError` and Zod errors to HTTP responses — do not add HTTP status logic anywhere else
- Wrap infrastructure errors (Docker, filesystem) in domain-specific errors with context preserved in the `cause` field

### Client

- `apiFetch<T>()` throws `ApiError` with `status` and `fields` — always handle it in hooks or form submit handlers
- Map `ApiError.fields` to react-hook-form field errors for form validation feedback
- Show user-facing feedback via `sonner` toasts for async operation outcomes

## API Layer

### Backend Routes

- Route files are `FastifyPluginAsyncZod` functions
- Define Zod body/params/querystring schemas inline in the route
- Authentication: attach `requireAuth` preHandler to all protected routes
- Route handlers must be thin — extract logic into services immediately if more than ~10 lines

### Frontend API Clients

- Each domain has its own client file in `client/src/lib/` (e.g., `stacks-api.ts`)
- All API calls go through `apiFetch<T>()` — never use `fetch` directly in components or hooks
- API client functions are pure: `(args) => Promise<T>`; no side effects
- Types for API responses are declared as interfaces in the API client file

---

## Real-time / SSE

- Container events and stack status changes flow through `StatePoller` (server) → SSE endpoint → `useContainerEvents` / `useLogStream` hooks (client)
- Do not poll the REST API for state that is available via SSE
- Hooks must close the `EventSource` in the cleanup function to prevent connection leaks

---

## Validation

- **All** request validation uses Zod schemas from `@docktor/shared`
- Shared schemas are the single source of truth — keep client and server in sync automatically
- Add new schemas to the appropriate file in `shared/src/validation/` and re-export from `shared/src/index.ts`
- Do not duplicate Zod schemas in the server or client

---

## Database

- Prisma schema is split into modular `.prisma` files under `server/prisma/schema/` — add new models in their own file
- Use Prisma transactions (`prisma.$transaction(...)`) for any operation that touches multiple tables
- Never use raw SQL unless Prisma cannot express the query
- Migrations are generated with `prisma migrate dev` — never edit migration files manually
- Prisma enum values must match the domain's `StackStatus` state machine

---

## Frontend UI

- Use **shadcn/ui** primitives from `components/ui/` — do not reinvent buttons, inputs, dialogs, etc.
- New domain-specific components go in `components/domain/`
- Reusable non-domain components go in `components/common/`
- Styling: **TailwindCSS v4** utility classes; use `clsx` + `tailwind-merge` (`cn()` helper) for conditional class names
- Use **CVA (class-variance-authority)** for components with multiple visual variants
- Forms: always use `react-hook-form` with a Zod resolver — no uncontrolled or ad-hoc form state

---

## Code Quality & Refactoring

- Run `tsc --build` before every commit — zero type errors allowed
- Refactor **proactively** when touching a module: extract duplicated logic, improve names, tighten types
- Remove dead code; do not leave commented-out blocks
- Avoid `any` casts such as `as any` — if one exists, replace it with a proper type
- Keep functions and methods short; extract helpers if a function exceeds ~30 lines
- SonarQube is the quality gate — do not suppress issues without a justified comment
- Add inline comments only where the intent is not obvious from the code itself

## Import Conventions

| Workspace | Style | Example |
|-----------|-------|---------|
| `client` | Absolute via `@/*` alias | `import { useStacks } from "@/hooks/use-stacks"` |
| `server` | Relative with `.js` extension (ESM) | `import { stackRepository } from "../repositories/index.js"` |
| Both | Shared schemas | `import { CreateStackInput } from "@docktor/shared"` |

- Do not create barrel `index.ts` files for a single module
- Group imports: external packages → workspace packages → local modules (blank line between groups)

## Git & Commits

- One logical change per commit; keep commits atomic and reviewable
- Commit message format: `type(scope): description` (e.g., `feat(stacks): add deploy cancellation`)
- Types: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`
- Never commit with failing tests or type errors
- Feature work on `feature/*` branches; merge to `main` via PR

## Issue Tracking

Docktor tracks product work in **GitHub Issues** (`docktor-app/docktor`), not in `.planning/`. This is a deliberate split:

- **GitHub Issues = what and why.** Outcome-shaped, written from the user's perspective, the public interface of the project. Granularity: one issue a contributor could pick up. This is where features, bugs, chores, and docs work live.
- **`.planning/` = how.** GSD phases, plans, and technical sequencing for whoever (human or agent) is implementing an issue. Stays an implementation detail, may be far more granular than the issue it serves, and is not mirrored 1:1 with GitHub.

### Capturing new work (`gsd-capture` / `/gsd-capture`)

**Project-specific override:** the default GSD `add-todo` workflow writes to `.planning/todos/pending/*.md`. For this project, skip that — when a session surfaces a user-facing idea, bug, or chore worth tracking, create a GitHub issue directly instead:

```bash
gh issue create --repo docktor-app/docktor --title "[TYPE] Outcome-shaped title" --body-file <file> --label "area:<area>"
```

Then set the issue's **Issue Type** field (see below). The installed `gh` CLI (2.45.0) has no flag for this yet — set it via the GitHub UI, or via the GraphQL API:

```bash
gh api graphql -f query='mutation($issueId:ID!,$issueTypeId:ID!){
  updateIssueIssueType(input:{issueId:$issueId, issueTypeId:$issueTypeId}) { issue { number } }
}' -f issueId="<issue node id>" -f issueTypeId="<type node id>"
```

Get node IDs via `gh api repos/docktor-app/docktor/issues/<n> --jq .node_id` and `gh api orgs/docktor-app/issue-types --jq '.[] | {name,node_id}'`.

Use `.planning/todos/` (or a debug session, or an inline fix) only for things that are genuinely internal GSD micro-tasks — not something a contributor would ever pick up as a standalone unit of work (e.g., "reorder these two lines in a plan file"). If in doubt, it's a GitHub issue.

Before creating: search existing open issues (`gh issue list --repo docktor-app/docktor`) and extend/comment on a near-duplicate rather than opening a new one.

### Issue Type (native GitHub field — not a label)

The org has these Issue Types configured: **Bug**, **Feature**, **Chore**, **Documentation**, **Task**. Set the native type field on every new issue — do not encode type as a `[BUG]`/`[FEATURE]` title prefix or a `type:*` label; both predate the native field and are legacy on the handful of pre-existing issues that still carry them. Don't propagate that pattern to new issues.

### Labels

Use `area:*` labels to indicate the affected subsystem: `area:server`, `area:client`, `area:proxy`, `area:backup`, `area:templates`, `area:auth`, `area:ci`. Multiple areas may apply. Meta labels `good first issue`, `help wanted`, `needs-design`, `blocked` are available for triage signals.

### Project board & fields

All issues live on the **"docktor Feature & Roadmap"** project (org-level). Relevant fields:

- **Status**: `Backlog` → `Ready` → `In progress` → `In review` → `Done`. New issues start in `Backlog`.
- **Priority**, **Size**: set during milestone/roadmap planning, not at capture time.
- **Milestone**: the target release (currently `v0.1.0 - First Release`). Milestone assignment is a deliberate scoping decision, not automatic on creation — new issues are created unassigned.
- **Parent issue / sub-issues**: use GitHub's native sub-issue relationship (`gh api repos/{owner}/{repo}/issues/{number}/sub_issues`) to link a narrower issue under a broader epic instead of duplicating the epic's scope.

### Issue body format

```markdown
## Context
Why this matters, one short paragraph, from the user's point of view.

## Acceptance criteria
- [ ] Observable, testable statements
- [ ] Each one checkable without reading the code

## Out of scope
What this issue deliberately does not cover, with a link to the follow-up if one exists.

## Notes
Technical constraints, affected workspaces, related issues.
```

Titles are imperative and outcome-shaped ("Show per-service health status on the dashboard"), not implementation-shaped ("Implement HealthCheckService").

### Linking implementation back to issues

Each `.planning/phases/*/PLAN.md` references the GitHub issue(s) it implements at the top. Each PR closes with `Closes #<n>` so the issue auto-closes on merge.

## Common Pitfalls to Avoid

- **Do not** import Prisma client outside `repositories/` or `lib/database.ts`
- **Do not** put business logic in route handlers
- **Do not** fetch data directly in React components — use a custom hook
- **Do not** edit files in `components/ui/` (shadcn-managed)
- **Do not** duplicate Zod schemas — add to `@docktor/shared`
- **Do not** use `as any` — model the type correctly
- **Do not** add HTTP status codes outside `lib/errors.ts` and `app.ts`
- **Do not** skip tests to ship faster — tests are part of the feature
